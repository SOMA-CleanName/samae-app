# 39. 사진 목적 분류 원칙 (2026-09-14)

> 문서 상태: **대분류·텍스트 우선 자동 분류 적용 완료 · 세부분류 적용 보류**
> 다중 목적: 2026-09-15 구현 및 실제 앱 DB `0116` 반영 완료
>
> 적용 범위: 어드민의 `사진 목적&무드` 작업 화면에서 사용할 내부 전용 사진 목적 태그

## 1. 목표

사진과 포트폴리오를 사용자가 사진을 찍으려는 **목적**에 따라 분류한다.

- 목적 태그는 운영자가 분류와 검색 품질을 관리하기 위한 내부 정보다.
- 일반 사용자 화면을 포함한 다른 화면에는 노출하지 않는다.
- 기본 분류 단위는 포트폴리오이며, 포트폴리오에 지정한 대분류 목록을 소속 사진 전체에 적용한다. 사진 하나에 `웨딩`과 `반려동물`처럼 여러 목적을 함께 지정할 수 있다.
- 포트폴리오 안에 목적이 다른 사진이 섞여 있으면 해당 사진에만 다른 값을 지정할 수 있어야 한다.
- 기존 무드 태그, 생성 태그, 카테고리 및 관련 DB 필드는 수정하거나 재사용하지 않는다. 작가가 직접 입력한 `mood_tags`는 목적 판단용 텍스트로 읽을 수 있지만 값은 절대 변경하지 않는다.

## 2. 확정 대분류

현재 사용할 사진 목적 대분류는 다음 7개다.

1. 개인
2. 커플
3. 우정
4. 웨딩
5. 반려동물
6. 상업/브랜드
7. 행사

`미분류`는 사진 목적이 아니라 **분류 상태**다. 목적을 판단하지 못한 포트폴리오와 사진은 별도의 `기타` 목적에 넣지 않고 미분류 상태로 남겨 수동 검수한다.

## 3. 세부분류 체계

아래 세부분류는 향후 사용할 분류 구조로만 정의한다. **현재 단계에서는 세부분류를 판별하거나 저장하지 않는다.**

| 대분류 | 예정 세부분류 |
|---|---|
| 개인 | 개인 스냅, 프로필, 증명/여권 |
| 커플 | 커플 스냅 |
| 우정 | 우정 스냅 |
| 웨딩 | 웨딩 사진, 웨딩 스냅 |
| 반려동물 | 미정 |
| 상업/브랜드 | 상업, 브랜드, 쇼핑몰, 비즈니스 프로필, 제품, 광고 |
| 행사 | 단체 사진, 돌, 만삭, 아기, 졸업, 연회, 동호회 |

### 3.1 용어 경계

- `단체 사진`, `돌`, `만삭`, `아기`, `졸업`, `연회`, `동호회`는 독립 대분류가 아니라 모두 `행사`의 세부분류로 취급한다.
- `웨딩 사진`과 `웨딩 스냅`의 구체적인 판별 기준은 세부분류 작업을 시작할 때 별도로 정한다.
- `반려동물`의 세부분류는 아직 만들지 않는다.
- 한 사진이 여러 세부분류 후보에 해당하더라도 현재 단계에서는 대분류만 지정한다.

## 4. 현재 분류 단계

이번 단계에서 수행하는 작업은 대분류 지정까지만이다.

```text
포트폴리오 확인
  → 해당하는 대분류 1개 이상 선택
  → 포트폴리오 내 모든 사진에 일괄 적용
  → 예외 사진이 있으면 사진 단위로 대분류 재지정
```

이번 단계에서 하지 않는 작업:

- 세부분류 자동 판별
- 세부분류 수동 지정
- 세부분류 값 저장
- 무드 분류 또는 무드 태그 변경
- 기존 목적·카테고리·태그 필드 변경
- 일반 사용자 화면에 목적 태그 노출

## 5. 분류 원칙

- **SigLIP 1차 자동 분류에서 확정하는 목적은 반드시 1개만 선택·저장한다. 복수 목적 지정은 운영자의 수동 적용에서만 허용한다.** 텍스트·SigLIP 혼합 자동 분류에도 같은 단일 목적 원칙을 적용한다.
- 자동 분류 근거에 여러 후보와 점수를 남겨도 확정된 목적을 여러 개 저장하는 것은 아니다. 기존 임계값·충돌 기준에 따라 미분류로 보류하는 정책과 수동 검수값 보호는 유지한다.
- 설명이나 사진만으로 대분류를 확신하기 어려우면 임의로 지정하지 않고 미분류 상태로 둔다.
- 포트폴리오의 대분류와 다른 목적이 명백한 사진만 사진 단위 예외로 처리한다.
- 세부분류에 해당하는 단서가 보여도 현재는 대분류까지만 기록한다. 예를 들어 만삭 촬영은 현재 `행사`까지만 지정한다.
- 목적과 무드는 분리한다. 빈티지, 자연스러움, 따뜻함 등의 느낌은 목적 분류에 사용하지 않는다.

## 6. 확정된 자동 분류 방식

### 6.1 입력과 판정 순서

- 유료 외부 모델을 사용하지 않는다.
- 포트폴리오·사진 제목과 설명, 연결된 실제 패키지 이름과 설명, 작가 작성 해시태그, 타깃·탐색 카테고리를 먼저 판정한다.
- 목적을 직접 나타내는 텍스트가 있으면 해당 텍스트 판정을 우선한다.
- 텍스트에 목적 단서가 없을 때 기존 사진 임베딩과 같은 `google/siglip2-so400m-patch16-naflex` 점수를 사용한다.
- 여러 서비스를 나열한 텍스트는 후보 목적을 제한하고, 그 후보 안에서 SigLIP 점수가 높은 목적을 고른다.
- 강한 텍스트 근거끼리 충돌하면 임의로 확정하지 않고 미분류 상태로 남긴다.
- 기존 `photos.embedding`을 재사용하며 1차 목적 분류를 위해 사진을 다시 내려받거나 이미지 임베딩을 다시 만들지 않는다.
- 대분류별 영어 프롬프트 묶음을 SigLIP 텍스트 타워로 임베딩하고 사진 임베딩과 비교한다.
- 세부분류는 저장하지 않는다. 다만 `행사`처럼 범위가 넓은 대분류는 단체·돌·만삭·아기·졸업·연회·동호회 장면 프롬프트를 대분류 판별 근거로만 사용한다.

### 6.2 저장 위치

별도 분류 테이블을 만들지 않고 `albums`와 `photos`에 목적 전용 신규 컬럼을 직접 추가한다. API에서 조회 가능한 것은 허용하며, 일반 사용자 화면의 쿼리와 컴포넌트에서 표시하지 않는 것을 비노출 기준으로 삼는다.

두 테이블의 공통 신규 컬럼:

| 컬럼 | 의미 |
|---|---|
| `admin_purposes` | 확정된 대분류 목록(`text[]`, `0116`). 미분류는 빈 배열 |
| `admin_purpose` | 기존 자동 분류·백필 호환용 첫 번째 대분류. 목록 첫 항목과 동기화하며 미분류는 `null` |
| `admin_purpose_confidence` | 0~1 상대 확신도. 실제 확률로 해석하지 않음 |
| `admin_purpose_source` | `siglip`, `text`, `hybrid`, `manual` 중 하나 |
| `admin_purpose_reviewed` | 운영자가 확인했는지 여부 |
| `admin_purpose_version` | 모델·프롬프트·집계 규칙 버전 |
| `admin_purpose_at` | 자동 또는 수동 분류 처리 시각 |
| `admin_purpose_evidence` | 사용한 텍스트 구절, 후보 목적, SigLIP 후보 등 운영 검수 근거 |

`photos`에만 추가하는 컬럼:

| 컬럼 | 의미 |
|---|---|
| `admin_purpose_overridden` | `true`면 포트폴리오 일괄값 대신 사진에 지정한 예외값 유지 |
| `title` | 사진별 선택 제목 |
| `caption` | 사진별 선택 설명·캡션 |

`0117`부터 패키지 지정은 작가 선택과 관리자 내부 지정을 분리한다. 같은 작가에게 등록된 패키지만 연결할 수 있다.

| 저장 위치 | 용도 | 표시 및 우선순위 |
|---|---|---|
| `albums.package_id`, `albums.price_krw` | 작가가 직접 선택한 상품과 가격 | 작가 화면에 표시하며 항상 우선한다. |
| `album_admin_packages` | 관리자 수동 지정 또는 가격 대조 결과 | 운영자만 조회한다. 작가·고객에게 지정 여부를 표시하지 않는다. |

관리자 지정은 작가 선택값·사진 가격을 변경하지 않는다. 관리자 화면은 `작가 지정`과 `관리자 지정`을 구분하며, 작가가 이미 선택한 상품은 운영자가 변경할 수 없다. 작가가 나중에 패키지를 저장하면 DB 트리거가 내부 지정을 삭제하고 작가 선택을 적용한다. 이후 작가가 선택을 해제해도 삭제된 내부값이 되살아나지 않는다. 패키지를 고르지 않은 상태에서 설명만 저장하는 경우에는 내부 지정을 유지한다.

내부 지정 RPC `set_album_admin_package`는 관리자 권한·같은 작가 상품·작가 선택 여부를 검증한다. 앨범 행 잠금으로 동시 저장 시에도 작가 선택을 보호한다. 내부 테이블은 RLS로 일반 작가의 조회를 차단하며, 관리자 변경은 이 RPC를 통해서만 허용한다.

목적 분류 입력 역시 작가 선택을 우선하고, 작가 선택이 없으면 내부 지정 상품을 참고한다. 내부 상품에 매칭된 텍스트는 작가가 조회할 수 있는 `albums/photos.admin_purpose_evidence`에 저장하지 않는다. SigLIP 1차 분류는 여전히 목적 하나만 고른다.

`0115` 이전 업로드는 패키지 선택 시 상품 ID 대신 `photos.price_krw`에 가격만 저장했다. 검수 화면은 작가에게 등록된 패키지 개수와 포트폴리오의 상품 지정 상태를 구분한다. 관리자 화면의 `상품 미지정`은 작가 선택과 내부 지정이 모두 비어 있다는 뜻이며, 작가가 패키지를 등록하지 않았다는 뜻이 아니다. 선택 사진의 기존 가격과 각 패키지의 가격을 함께 보여준다.

포트폴리오 분류표에는 `상품 지정`과 `상품 미지정` 개수를 나란히 표시하며, 누르면 해당 포트폴리오만 보여준다. 작가 선택 또는 관리자 내부 지정이 있으면 `상품 지정`에 포함한다. 두 집계는 앨범이 있는 포트폴리오 기준이며 단독 사진은 제외한다. 지정·해제 후 개수와 목록도 함께 갱신한다.

기존 자료의 대조 도구는 `scripts/backfill-portfolio-packages.cjs`다. 기본 실행은 조회와 보고서 저장만 수행하고, `--apply`를 붙이면 다음 조건을 모두 만족하는 포트폴리오를 연결한다.

- 작가 선택과 기존 내부 지정이 모두 비어 있고, 모든 소속 사진에 같은 가격이 저장돼 있어야 한다. 비공개 사진도 함께 확인한다.
- 같은 작가에게 등록된 동일 가격 상품이 정확히 하나여야 한다. 비활성 상품도 후보에 포함해 중복 가격을 놓치지 않는다.
- 이미 저장된 포트폴리오 가격이 있다면 사진 가격과 같아야 한다.

조건을 만족하면 `album_admin_packages`에 내부 지정만 저장한다. 가격 누락·불일치, 동일 가격 상품 중복, 일치 상품 없음, 사진 없음은 확인 목록에 남긴다. 다른 작가의 상품이나 목적·이름 유사도는 연결 근거로 사용하지 않는다. 기존 작가·관리자 지정은 보존하며, 앨범·사진의 가격과 목적·검수 결과는 변경하지 않는다.

```bash
node scripts/backfill-portfolio-packages.cjs
node scripts/backfill-portfolio-packages.cjs --apply
```

`.env.local`의 `SUPABASE_DB_POOLER_URL` 또는 `SUPABASE_DB_URL`로 앱과 같은 Supabase 프로젝트에 접속한다. 적용 전 대조 목록과 원래 연결·가격은 `scripts/embed/out/package-links/<실행 시각>-apply/report.json`에 기록하고, 남은 항목과 상품 후보는 같은 폴더의 `needs-review.csv`에 저장한다. 짧은 트랜잭션 안에서 관련 테이블 변경을 잠시 잠그고, 계획한 연결 및 나머지 데이터 보존을 검증한 뒤 커밋한다.

2026-09-15 가격 대조한 119개 포트폴리오를 운영자 요청에 따라 내부 지정으로 이관했다. 이전 실행 보고서와 적용 당시 값·시각이 일치하는 항목만 이동하고, 작가용 상품·앨범 가격 칸은 대조 전 값으로 돌렸다. 사진 가격과 목적·검수 데이터는 보존했다. 공개 포트폴리오 연결은 118개이며, 관리자 화면의 상품 미지정은 55개다. 공개 자료 중 남은 항목은 동일 가격 상품 중복 15개, 일치 상품 없음 12개, 가격 없음 27개, 사진 가격 불일치 1개다.

가격 값이 없거나 유효하지 않으면 `가격 확인 필요`로 표시한다. 서버에서 새 데이터를 받으면 현재 필터·사진 선택을 유지하면서 목록과 가격을 갱신한다.

허용하는 저장 코드는 `personal`, `couple`, `friendship`, `wedding`, `pet`, `commercial`, `event`다. 화면에서는 각각 개인, 커플, 우정, 웨딩, 반려동물, 상업/브랜드, 행사로 표시한다.

`mood_tags`, 타깃 카테고리, 탐색 카테고리는 분류 입력으로 읽을 수 있다. `generated_tags`, `auto_mood_tags`는 입력에서도 제외한다. 이 기능은 기존 태그·카테고리 열을 쓰거나 변경하지 않는다.

### 6.3 포트폴리오와 사진의 관계

- 1차 자동 분류는 포트폴리오 단위로 결정한다.
- 확정된 포트폴리오의 목적 목록 전체를 소속 사진의 `admin_purposes`에도 실제로 일괄 저장한다.
- 포트폴리오 목적을 나중에 수정하면 `admin_purpose_overridden=false`인 사진의 목록을 함께 교체한다.
- `admin_purpose_overridden=true`인 사진은 포트폴리오 목적이 바뀌어도 기존 사진 목적을 유지한다.
- 사진별 예외를 해제하면 포트폴리오의 목적 목록 전체를 다시 상속한다. 단독 사진의 예외를 해제하면 미분류로 돌아간다.
- 이번 1차 분류에서는 사진별 자동 예외를 만들지 않는다. 운영자가 명백히 다른 사진을 확인했을 때만 사진 예외를 지정한다.

### 6.4 적용 순서

1. 전체 공개 포트폴리오를 대상으로 dry-run한다.
2. 목적별 분포와 1·2위 점수 차이가 작은 경계 사례를 검토한다.
3. 검토 결과로 자동 적용 기준을 정한다.
4. 기준 이상 포트폴리오와 소속 사진에 목적값을 저장한다.
5. 기준 미만 포트폴리오는 `admin_purpose=null`로 남겨 수동 검수한다.
6. 자동 저장 결과는 판정 방식에 따라 `admin_purpose_source='text'`, `'hybrid'`, `'siglip'` 중 하나와 `admin_purpose_reviewed=false`로 기록한다.
7. 운영자가 확정하거나 수정하면 `admin_purpose_source='manual'`, `admin_purpose_reviewed=true`로 바꾼다.

분류 배치는 dry-run이 기본이며 명시적인 apply 옵션이 있어야 DB에 쓴다. 재실행할 때는 운영자가 검수한 값과 사진별 예외를 덮어쓰지 않는다.

기본 모드는 위 보수적 기준을 유지한다. 전체 자동 분류가 필요할 때만 `--force-all`을 명시하며, 이 모드는 공개 여부와 임계값·중앙값/다수결 충돌에 관계없이 포트폴리오 중앙값 점수 1위를 저장한다. 이 경우에도 수동 검수값과 사진별 예외는 덮어쓰지 않는다.

상세 설계: [SigLIP 사진 목적 분류 설계](superpowers/specs/2026-09-14-photo-purpose-classification-design.md)

목적 문장 임베딩도 같은 상주 모델의 `/embed-text-backfill`을 사용해 검색에 양보한다. 대상 0개는 정상 종료하고, 사진 단계 일부 실패 시에도 목적 처리를 이어가되 전체 배치는 실패로 기록한다. 변경이 없는 현재 버전은 건너뛴다. 자세한 반영·실행·로그 확인은 [28 문서 §9](28-embedding-batch-automation.md#daily-purpose)를 따른다.

## 9. 여러 목적을 함께 지정하기 (2026-09-15)

`사진 목적`에서 해당 항목을 여러 개 선택한다. 선택한 항목을 다시 누르면 해제된다. 선택만으로 저장하지 않으며, 선택 영역 아래의 **포트폴리오 전체에 적용** 또는 **선택한 사진만 개별 적용**으로 확정한다. 최소 한 개를 선택해야 적용할 수 있다.

`저신뢰` 목록과 개수는 자동 분류 신뢰도가 0.8 미만이며 아직 검수하지 않은 포트폴리오만 포함한다. 포트폴리오 검수를 완료하면 즉시 저신뢰에서 빠지고, 당시 자동 분류 신뢰도 자체는 기록으로 보존한다.

`검수 미완료`는 신뢰도와 분류 여부에 관계없이 아직 포트폴리오 검수를 완료하지 않은 항목을 모은다. 포트폴리오 검수 완료 시 목록과 개수에서 즉시 빠진다. 단독 사진은 해당 사진의 검수 상태를 기준으로 한다.

왼쪽 필터 아래의 `목적별 집계`는 필터와 관계없이 이 화면에 불러온 전체 공개 사진을 기준으로 한다. 포트폴리오 수는 포트폴리오 자체에 지정된 목적을, 사진 수는 개별 사진에 지정된 목적을 각각 센다. 사진별 예외가 포트폴리오의 목적 개수를 바꾸지는 않는다. 단독 사진은 사진 수에만 포함한다. 복수 목적은 각 목적에 한 번씩 포함하고, `전체` 행은 목적 수와 관계없이 각 포트폴리오·사진을 한 번만 센다. 목적 저장·예외 변경·서버 재조회 시 집계도 갱신된다.

예를 들어 강아지를 안고 찍은 웨딩 사진에는 `웨딩`·`반려동물`을 선택하고 사진만 개별 적용한다. 나머지 사진의 분류는 유지된다. 사진 배지에는 저장된 목적을 모두 표시하며 목적 필터는 포트폴리오 또는 소속 사진에 포함된 목적을 찾는다.

저장소의 [0116 마이그레이션](../supabase/migrations/0116_multiple_photo_purposes.sql)을 앱 DB에 먼저 적용한다. 기존 단일 목적과 검수·신뢰도·출처·근거는 보존하고 목적 목록을 채운다. 기존 단일 목적 RPC와 자동 백필도 계속 동작한다. 자동 분류는 수동 확정·검수한 목적 목록과 사진별 예외를 덮어쓰지 않는다.

DB 접속 설정이 있으면 프로젝트의 기존 실행기를 사용한다.

```bash
node scripts/apply-migration.cjs supabase/migrations/0116_multiple_photo_purposes.sql
```

또는 같은 Supabase 프로젝트의 SQL Editor에서 파일 전체를 한 번 실행한다. 적용 전에는 앱이 기존 단일 목적 데이터로 화면을 열고 DB 업데이트 안내를 표시하며, 복수 목적 저장을 비활성화한다. 적용 후 화면을 새로고침한다.

저장 로직은 격리 PostgreSQL 16에서 [SQL 통합 테스트](../supabase/tests/photo-purpose-multiple.sql)로 검증한다. 테스트는 이름이 `samae_purpose_qa`이고 테이블이 없는 별도 DB만 허용하며, 기존 `0113`~`0115`와 `0116`을 실행한 뒤 전체 트랜잭션을 롤백한다. 운영 DB에 테스트 스크립트를 실행하지 않는다.

2026-09-15 실제 앱 DB(PostgreSQL 17.6)에 `0116` 적용을 완료하고 `_migrations`에 기록했다. 포트폴리오 177개와 사진 1,817개의 기존 데이터는 `updated_at`을 제외한 전체 행 해시로 보존을 확인했으며, 기존 단일 목적과 이관한 목록의 불일치는 0건이다. 웨딩·반려동물 복수 저장, 포트폴리오 상속, 사진 예외 보호·해제, 기존 단일 RPC 호환을 같은 트랜잭션에서 검증하고 시험 변경을 롤백한 뒤 마이그레이션을 커밋했다.

목적 변경 가드는 `SECURITY DEFINER`로 바뀌는 함수 소유자 대신 호출 세션의 역할과 관리자 프로필을 확인한다. 실제 DB에서 일반 로그인 사용자의 RPC 호출 거부와 관리자·서비스 역할의 저장 성공을 확인했다. 앱의 실제 데이터 조회에서도 복수 목적 스키마 인식과 포트폴리오 173개 조회가 확인됐다. 적용된 DB에서 `0116`을 다시 실행하지 않는다.
