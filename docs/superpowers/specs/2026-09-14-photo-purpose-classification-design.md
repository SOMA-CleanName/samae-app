# SigLIP 사진 목적 분류 설계

> 작성일: 2026-09-14
>
> 상태: 구현 및 1차 백필 완료
>
> 기준 문서: [사진 목적 분류 원칙](../../35-photo-purpose-taxonomy.md)

## 1. 목적

공개 포트폴리오와 소속 사진에 내부 운영용 촬영 목적 대분류를 1차로 부여한다. 분류 모델은 추가 API 비용이 들지 않는 기존 SigLIP2만 사용한다.

목적 대분류는 다음 7개다.

| 저장 코드 | 화면 표시 |
|---|---|
| `personal` | 개인 |
| `couple` | 커플 |
| `friendship` | 우정 |
| `wedding` | 웨딩 |
| `pet` | 반려동물 |
| `commercial` | 상업/브랜드 |
| `event` | 행사 |

이번 범위는 대분류 저장까지다. 세부분류와 무드 분류는 포함하지 않는다.

## 2. 확정한 접근

### 2.1 선택안

`albums`와 `photos`에 목적 전용 컬럼을 직접 추가한다. 포트폴리오 단위로 자동 판정한 값을 앨범과 소속 사진에 함께 저장하고, 사진별 수동 예외는 덮어쓰기 플래그로 보호한다.

이 방식은 다음 요구사항을 우선한다.

- 앨범과 사진 각각에서 목적값을 직접 필터할 수 있다.
- 포트폴리오 목적을 사진 전체에 일괄 적용한다.
- 우연히 다른 사진이 섞이면 그 사진만 다른 목적을 유지할 수 있다.
- 기존 무드·검색·타겟 카테고리 필드와 값을 섞지 않는다.
- 목적 필드는 API에서 조회될 수 있지만 일반 사용자 화면에는 표시하지 않는다.

### 2.2 선택하지 않은 안

- 앨범값을 조회 시 사진에 상속: 값 중복은 없지만 사진 행에 실제 목적값이 저장되지 않아 요구사항과 다르다.
- 관리자 전용 별도 테이블: API 비공개가 필수가 아니므로 현재 범위에서는 불필요한 조인과 구조를 늘린다.
- 외부 VLM 보조 분류: 비용 0 원칙과 맞지 않는다.

## 3. 데이터 모델

### 3.1 공통 컬럼

`public.albums`와 `public.photos`에 다음 컬럼을 각각 추가한다.

| 컬럼 | 타입 | 기본값 | 규칙 |
|---|---|---|---|
| `admin_purpose` | `text` | `null` | 7개 코드 또는 `null` |
| `admin_purpose_confidence` | `real` | `null` | `0 <= value <= 1`; 상대 지표이며 확률 아님 |
| `admin_purpose_source` | `text` | `null` | `siglip`, `manual` 또는 `null` |
| `admin_purpose_reviewed` | `boolean` | `false` | 운영자 검수 여부 |
| `admin_purpose_version` | `text` | `null` | 예: `siglip2-so400m-naflex@purpose-v1` |
| `admin_purpose_at` | `timestamptz` | `null` | 마지막 목적 처리 시각 |

`public.photos`에만 다음 컬럼을 추가한다.

| 컬럼 | 타입 | 기본값 | 규칙 |
|---|---|---|---|
| `admin_purpose_overridden` | `boolean` | `false` | 사진별 예외면 `true` |

`text + check constraint`를 사용해 라벨 추가·이름 변경 시 PostgreSQL enum 타입을 교체하지 않아도 되게 한다. 제약조건은 이름과 대상 테이블을 확인하는 `DO` 블록으로 멱등하게 추가한다.

### 3.2 인덱스

어드민의 목적·검수 상태 필터를 위해 두 테이블에 `(admin_purpose_reviewed, admin_purpose)` 복합 인덱스를 하나씩 둔다. 데이터 규모가 작고 쓰기 비용을 늘릴 필요가 없으므로 목적 관련 인덱스를 더 만들지 않는다.

### 3.3 기존 컬럼과 격리

다음 컬럼과 테이블은 마이그레이션, 분류 배치, 어드민 저장 액션의 읽기·쓰기 대상에서 제외한다.

- `photos.mood_tags`
- `photos.generated_tags`
- `photos.auto_mood_tags`
- `albums.target_category_id`
- `categories`, `explore_categories` 및 멤버십 테이블

기존 `photos.embedding`, `photos.embedding_model`, `photos.embedded_at`은 분류 입력과 호환성 검사에만 읽는다.

## 4. SigLIP 분류기

### 4.1 입력

대상은 공개 사진이 한 장 이상 있고, 해당 공개 사진에 현재 모델의 임베딩이 있는 포트폴리오다. 임베딩이 없거나 모델 버전·차원이 맞지 않는 사진은 그 포트폴리오 집계에서 제외한다. 유효 사진이 한 장도 없으면 포트폴리오를 미분류로 남긴다.

사진 파일과 썸네일은 내려받지 않는다. 저장된 1152차원 정규화 임베딩만 읽는다.

### 4.2 프롬프트 어휘

각 대분류에 같은 수의 영어 캡션형 프롬프트를 둔다. 단어 하나가 아니라 SigLIP이 학습한 이미지 캡션에 가까운 문장을 쓴다.

- 개인: 개인 스냅, 단독 인물, 프로필, 증명사진
- 커플: 데이트, 연인, 캐주얼 커플 촬영
- 우정: 친구 둘, 여러 친구, 우정 촬영
- 웨딩: 신랑·신부, 웨딩드레스, 야외 웨딩, 예식
- 반려동물: 반려동물 단독, 반려인 동반
- 상업/브랜드: 패션 룩북, 쇼핑몰, 제품 광고, 비즈니스 프로필
- 행사: 단체, 돌·첫돌, 만삭, 아기, 졸업, 연회, 동호회

세부분류 단어는 `event` 점수를 구성하기 위한 시각 프로토타입일 뿐 별도 값으로 저장하지 않는다. 프롬프트 수 차이에 따른 최대값 편향을 막기 위해 모든 대분류의 프롬프트 수를 동일하게 맞춘다.

프롬프트 집합과 집계 공식을 함께 버전 관리한다. 둘 중 하나가 바뀌면 `purpose-vN`을 올린다.

### 4.3 사진 점수

1. 모든 대상 사진 임베딩과 모든 목적 프롬프트 임베딩의 코사인 유사도를 계산한다.
2. 프롬프트마다 전체 사진 카탈로그를 기준으로 z-score를 계산해 문장별 점수 편향을 줄인다.
3. 한 대분류의 사진 점수는 그 대분류 프롬프트 z-score 중 최댓값으로 둔다.
4. 사진의 임시 예측은 대분류 점수 1위다.

SigLIP의 sigmoid 출력이나 코사인 값을 실제 확률로 해석하지 않는다.

### 4.4 포트폴리오 점수

1. 각 대분류에 대해 소속 사진 점수의 중앙값을 구한다.
2. 사진별 임시 예측에서 가장 많은 표를 받은 대분류를 구한다.
3. 중앙값 1위와 다수결 1위가 같을 때만 그 대분류를 포트폴리오 후보로 인정한다.
4. 두 결과가 다르면 자동 저장하지 않고 미분류로 보낸다.
5. 상대 확신도는 1·2위 중앙값 차이와 다수결 비율을 함께 사용해 0~1로 정규화한다. 이 값은 자동 적용 순서와 필터용이며 확률이 아니다.

포트폴리오에 목적이 다른 사진이 일부 섞여 있어도 중앙값과 다수결이 대표 목적을 유지하도록 한다. 반대로 사진별 결과가 크게 갈리는 포트폴리오는 미분류로 보낸다.

## 5. 자동 적용 기준

임계값은 코드 작성 전에 추정하지 않는다. 전체 dry-run 결과를 낸 뒤 다음 자료를 보고 정한다.

- 목적별 포트폴리오 수와 사진 수
- 확신도 구간별 분포
- 1·2위 점수 차이가 작은 포트폴리오
- 중앙값 1위와 다수결 1위가 충돌한 포트폴리오
- 각 목적의 고득점·경계 사례 이미지 시트
- 현재 설명에서 목적이 명확한 포트폴리오와의 일치 여부

기준 이상은 자동 저장하고 기준 미만 또는 신호 충돌은 `admin_purpose=null`로 유지한다. 낮은 확신을 억지로 `기타`에 넣지 않는다.

앨범 설명의 키워드는 검토 자료로는 보여주지만 1차 SigLIP 점수나 자동 판정에는 섞지 않는다. 이로써 SigLIP 단독 성능을 먼저 측정한다. 필요성이 실측되면 별도 설계 변경으로 추가한다.

## 6. 저장과 상속

### 6.1 최초 백필

자동 적용된 포트폴리오는 앨범과 그 포트폴리오에 속한 모든 사진에 동일한 값을 기록한다. 포트폴리오 판정에는 공개·임베딩 보유 사진만 사용하지만, 일괄 적용은 사진의 공개 여부와 관계없이 수행한다.

- `admin_purpose=<7개 코드 중 하나>`
- `admin_purpose_confidence=<상대 확신도>`
- `admin_purpose_source='siglip'`
- `admin_purpose_reviewed=false`
- `admin_purpose_version=<현재 분류기 버전>`
- `admin_purpose_at=<UTC 시각>`
- 사진의 `admin_purpose_overridden=false`

미분류 포트폴리오와 그 소속 사진은 `admin_purpose`를 `null`로 유지하되, 배치가 처리했다는 사실을 구분할 수 있도록 버전과 처리 시각을 기록한다.

### 6.2 운영자 수정

포트폴리오 목적을 운영자가 지정하거나 바꾸면 앨범과 `admin_purpose_overridden=false`인 모든 소속 사진을 한 작업으로 갱신한다. 부분 성공으로 앨범과 사진이 어긋나지 않게 서버의 단일 DB 함수 또는 트랜잭션 경계 안에서 실행한다.

사진 하나를 다르게 지정하면 해당 사진의 목적을 저장하고 `admin_purpose_overridden=true`, `admin_purpose_source='manual'`, `admin_purpose_reviewed=true`로 바꾼다.

사진 예외를 해제하면 `admin_purpose_overridden=false`로 바꾸고 현재 포트폴리오 목적과 메타데이터를 다시 복사한다.

### 6.3 재분류 보호

배치는 다음 행을 덮어쓰지 않는다.

- `admin_purpose_reviewed=true`
- `admin_purpose_source='manual'`
- `photos.admin_purpose_overridden=true`

모델 또는 프롬프트 버전이 바뀌더라도 검수되지 않은 SigLIP 결과만 재분류 대상으로 삼는다.

## 7. 배치 인터페이스와 안전장치

기존 임베딩 배치 스크립트 패턴을 따른다.

- 기본 실행은 dry-run이다.
- `--apply`가 있어야 DB를 변경한다.
- `--limit`으로 소량 쓰기 검증을 지원한다.
- 모든 update는 ID 또는 album ID로 대상을 한정한다.
- 실행 전 대상 수, 모델 호환 수, 제외 수를 출력한다.
- 실행 후 DB를 다시 조회해 적용 수와 미분류 수를 검증한다.
- 일부 저장이 실패하면 성공한 행은 유지하고 실패 대상을 보고한다. 재실행은 보호 규칙에 따라 안전해야 한다.

dry-run 산출물은 JSON/CSV 요약과 포트폴리오 대표 이미지 시트다. 이 파일은 검증 자료이며 DB 값이 아니다.

## 8. 어드민 UI 계약

목적 데이터는 일반 사용자 컴포넌트나 기존 공개 검색 결과 타입에 추가하지 않는다. 어드민 `사진 목적&무드` 화면만 목적 컬럼을 명시적으로 조회한다.

첫 구현에서 필요한 필터:

- 미분류: `admin_purpose is null`
- 자동분류: `admin_purpose_source='siglip'`
- 검수완료: `admin_purpose_reviewed=true`
- 목적별: `admin_purpose=<purpose>`
- 낮은 확신: 확정한 기준 미만

포트폴리오 편집은 사진 전체 일괄 적용을 기본으로 하며, 개별 사진 편집은 예외 덮어쓰기로 표시한다.

## 9. 오류 처리

- 모델 태그 또는 임베딩 차원이 다르면 해당 사진을 계산하지 않고 호환성 오류 수를 보고한다.
- 포트폴리오에 유효 임베딩이 없으면 DB 목적값을 만들지 않는다.
- NaN, 무한대, 표준편차 0인 프롬프트 점수는 실패 처리하고 apply를 중단한다.
- 허용 목록 밖의 목적 코드는 애플리케이션과 DB 제약조건 양쪽에서 거부한다.
- 포트폴리오 일괄 저장이 실패하면 해당 포트폴리오의 앨범·사진 변경 전체를 롤백한다.
- 일반 사용자 화면은 목적 컬럼을 읽지 않으므로 분류 실패의 영향을 받지 않는다.

## 10. 검증

### 10.1 단위 테스트

- 프롬프트 수가 모든 대분류에서 같은지 검사한다.
- 목적 코드 허용 목록과 화면 라벨 매핑을 검사한다.
- z-score, 대분류 최대값, 포트폴리오 중앙값, 다수결과 동률 처리를 검사한다.
- 상대 확신도가 0~1 범위를 벗어나지 않는지 검사한다.
- 수동·검수완료·사진 예외 행이 재분류에서 제외되는지 검사한다.

### 10.2 통합 검증

- dry-run은 DB를 변경하지 않는다.
- `--apply --limit`은 지정한 수보다 많은 포트폴리오를 변경하지 않는다.
- 포트폴리오 목적 변경이 예외가 아닌 사진에만 반영된다.
- 사진 예외 설정·해제가 포트폴리오 값과 올바르게 분리·복구된다.
- 기존 무드·생성 태그·타겟 카테고리 값의 전후 스냅샷이 동일하다.
- 일반 사용자 페이지와 검색 응답에 목적 필드가 새로 표시되지 않는다.

### 10.3 완료 기준

- 전체 대상 포트폴리오 dry-run 보고서가 생성된다.
- 운영자가 자동 적용 임계값을 검토해 확정한다.
- 마이그레이션 적용 뒤 신규 컬럼과 제약조건이 존재한다.
- 기준 이상 결과가 앨범과 소속 사진에 일치하게 저장된다.
- 기준 미만과 계산 불가 항목이 미분류로 남는다.
- 기존 목적·무드·검색 태그 관련 컬럼은 변경되지 않는다.

## 11. 배포와 되돌리기

1. 스키마 마이그레이션을 적용한다.
2. dry-run과 소량 apply로 저장·보호 규칙을 검증한다.
3. 전체 자동 적용 대상을 백필한다.
4. DB 재조회와 이미지 시트로 결과를 확인한다.
5. 어드민 UI를 연결한다.
