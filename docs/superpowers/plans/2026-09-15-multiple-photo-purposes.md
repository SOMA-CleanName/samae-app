# Multiple Photo Purposes Implementation Plan

**Goal:** 사진 목적을 여러 개 선택하고 포트폴리오 전체 또는 선택 사진에 저장한다.

**Architecture:** `admin_purposes text[]`를 추가하고 기존 `admin_purpose`는 첫 항목으로 동기화해 자동 백필과 기존 RPC의 계약을 유지한다. 수동 다중 저장은 새 원자적 RPC로 처리한다. UI는 배열을 편집하며 적용 버튼으로 확정한다.

**Scope:** 기존 7개 목적, 운영자 권한, 사진별 예외, 기존 검수·자동 분류 보호를 유지한다. SigLIP 1차 자동 분류에서 확정하는 목적은 반드시 1개만 선택·저장하며, 복수 목적은 운영자가 수동으로 지정할 때만 허용한다. 기존 미분류 보류 기준은 유지한다. 일반 사용자 지면에는 목적을 노출하지 않는다.

## 검증 및 적용 결과

- [x] 실제 앱 DB에 0116 적용 후 복수 저장·재조회 확인.

전체 TypeScript 테스트 301개와 관련 테스트 24개, TypeScript 검사, 변경 파일 ESLint, 프로덕션 빌드가 통과했다. 독립 리뷰에서 선택 순서 변경을 미적용으로 표시하지 않는 경미한 문제를 수정하고 재검토를 마쳤다.

PostgreSQL 16의 격리 DB에서 기존 0113~0115와 새 0116을 실제 실행했다. 기존 분류 이관, 복수 저장, 예외 보호·해제, 단일 RPC 호환, 자동 분류 보호, 유효성·권한 거부를 확인하고 전체 트랜잭션을 롤백했다. 실제 서비스의 모든 RLS 정책과 여러 세션의 동시 실행은 이 축약 스키마 테스트 범위 밖이다.

실제 React 서버 렌더링으로 목적 7개 중 웨딩·반려동물 동시 선택 표시, DB 업데이트 전 복수 적용 비활성화, 업데이트 후 적용 버튼 활성화를 확인했다. 실제 DB 적용 전에는 기존 단일 목적 조회 경로, 적용 후에는 `multiplePurposesReady=true`와 포트폴리오 173개의 정상 조회를 확인했다. Browser 연결은 `No browser is available`로 실패하여 실제 클릭·스크린샷 검증은 수행하지 못했다. 로컬 3000 앱과 8077 모델 서버는 모두 HTTP 200이다.

사용자가 제공한 SQL 접속 정보를 `.env.local`에 저장했다. 이 PC의 직접 주소는 DNS 조회가 실패했지만, `scripts/migrate.cjs`에 기록된 해당 프로젝트의 Session Pooler 주소로 연결했고 동작하는 `SUPABASE_DB_POOLER_URL`도 저장했다. `.env.local`은 Git에서 제외된다.

실제 DB의 `is_service_context()`를 확인하자 기존 테스트의 mock과 달리 `current_user`를 신뢰하고 있었다. 이 조건을 격리 테스트에 그대로 반영했을 때 `SECURITY DEFINER` RPC의 일반 사용자 거부 테스트가 실패했다. `0116`의 네 가드를 호출 세션의 역할 기반으로 수정한 뒤 실제 `SET ROLE`을 사용하는 전체 SQL 테스트를 다시 통과했고, 독립 리뷰에서도 중요한 문제는 발견되지 않았다.

실제 앱 DB PostgreSQL 17.6에서 `0116` 하나만 원자적으로 적용했다. 포트폴리오 177개와 사진 1,817개의 기존 데이터는 `updated_at`을 제외한 전체 행 해시가 동일했고, 목적 배열 이관 불일치는 0건이다. 서비스 역할로 복수 저장·재조회, 포트폴리오 상속, 사진 예외 보호·해제, 단일 RPC 호환을 확인했다. 실제 관리자 프로필로 저장에 성공했고, 관리자 프로필이 없는 `authenticated` 역할의 세 변경 RPC는 모두 거부됐다. 시험용 변경은 타임스탬프까지 롤백한 뒤 스키마·이관 결과와 `_migrations` 기록만 커밋하고 PostgREST 스키마 캐시를 갱신했다.

후속 검수 개선: 검수 완료 포트폴리오를 저신뢰 목록·개수에서 제외했다. 이전 업로드는 상품 ID 대신 사진 가격만 저장했으므로 패키지 상태를 `패키지 확인 필요`로 표시하고 기존 사진 가격과 상품별 가격을 노출했다. 상품 연결 데이터는 추정해 변경하지 않았다. 회귀 테스트를 추가해 전체 TypeScript 테스트 304개, TypeScript 검사, 변경 파일 ESLint가 통과했다. 실제 데이터 조회와 React 서버 렌더링으로 검수 완료 제외, 기존 선택 가격 120,000원과 해당 작가의 동일 가격 상품 표시를 확인했다.

가격 `NaN` 수정: `useState(initialAlbums)`가 이전 형식의 데이터를 유지하면서 새 서버 가격을 반영하지 않는 문제를 실제 React 컴포넌트 갱신으로 재현했다. 서버 입력이 바뀌면 목록 상태를 갱신하고 가격 누락·비정상 값에는 `가격 확인 필요`를 표시한다. 현재 필터 유지와 새 가격 120,000원 표시를 컴포넌트로 검증했고 전체 TypeScript 테스트 306개, TypeScript 검사, 변경 파일 ESLint가 통과했다. DB 패키지 61개의 가격은 모두 정상이었다. 컴포넌트 검증용 React 렌더러는 임시 폴더에만 설치했으며 프로젝트 의존성은 변경하지 않았다.

목적별 집계: 왼쪽 필터 아래에 목적별 포트폴리오 수·사진 수와 전체 합계를 추가했다. 포트폴리오 목적과 사진 예외를 따로 세고, 복수 목적은 각 목적에 포함하며 단독 사진은 사진 수에만 포함한다. 전체 TypeScript 테스트 309개, TypeScript 검사, 변경 파일 ESLint가 통과했다. 실제 화면 데이터(포트폴리오 173개·공개 사진 1,780장)의 7개 목적별 수치와 전체 합계가 독립 SQL 집계와 일치했다. 실제 React 컴포넌트 갱신으로 포트폴리오·사진 목적 변경 시 표 갱신 및 필터 변경과 무관한 전체 집계를 확인했다.

패키지 등록 재확인: 작가 16명에게 패키지 61개(활성 60개)가 등록돼 있고, 공개 포트폴리오 173개 모두 소유 작가의 등록 패키지가 있다. 포트폴리오 177개의 `package_id`는 비어 있다. 가장 최근 포트폴리오 등록은 2026-09-05이며, 상품 ID 저장 코드는 2026-09-15의 `8f78372`에서 추가됐다. 직전 코드의 업로드 선택값은 패키지 가격이고, 앨범 생성은 작가 ID·설명만 저장하며 사진에 가격을 기록했다. 현재 관계와 삭제 보관 자료(앨범 32개·사진 476개)에도 별도 상품 ID 연결은 없다. 공개 포트폴리오의 기존 가격을 대조하면 같은 작가의 현재 상품 후보가 하나인 자료 118개, 동일 가격 상품이 여러 개인 자료 15개, 현재 일치 상품이 없는 자료 12개, 가격이 없는 자료 27개, 사진별 가격이 일치하지 않는 자료 1개다. 이 조사는 읽기 전용이며 상품 연결을 추정해 저장하지 않았다. 화면에서는 작가 등록 패키지 개수를 표시하고 포트폴리오별 상태를 `상품 미지정`으로 구분했다.

패키지 대조 적용: 이후 운영자가 등록 패키지를 포트폴리오에 대조해 연결하도록 요청했다. `scripts/backfill-portfolio-packages.cjs`에서 기존 연결이 없고 모든 사진에 같은 가격이 저장된 포트폴리오를 같은 작가의 등록 상품과 비교했다. 비활성 상품을 포함해 동일 가격 후보가 하나인 경우에만 앨범 상품 ID와 가격을 저장한다. 누락·중복·불일치·다른 작가 상품 제외를 검증하는 Node 테스트 5개와 구문 검사를 통과했다.

실제 DB 트랜잭션으로 119개(공개 118개, 소속 사진 1,261장)의 연결을 저장했다. 적용 전후 전체 행 해시로 앨범의 연결·가격·수정 시각 외 정보와 사진·패키지 전체 데이터가 보존됐음을 확인했다. 적용 보고서와 변경 전 값은 `scripts/embed/out/package-links/2026-09-14T17-21-26-315Z-apply/report.json`, 남은 58개 항목과 후보는 같은 폴더의 `needs-review.csv`에 남겼다. 이 중 공개 자료는 55개이고, 나머지는 가격 없는 비공개 포트폴리오 1개와 빈 포트폴리오 2개다.

커밋 후 재조회에서 기존 연결 119개와 신규 대조 대상 0개를 확인했다. 실제 관리자 페이지 데이터에서 공개 포트폴리오 173개 중 연결 118개·미지정 55개가 조회됐다. 실제 React 컴포넌트에서 도토리 포트폴리오의 선택 상품이 `트윈/커플 스냅 · ₩120,000`으로 표시되는 것까지 검증했다. SigLIP 재분류나 검수 결과 변경은 수행하지 않았다.

관리자 지정 비노출·작가 우선: 운영자 요청에 따라 `0117_private_admin_portfolio_packages.sql`로 `album_admin_packages` 내부 테이블을 분리했다. 관리자 지정 RPC는 앨범 행 잠금 안에서 작가 선택 유무와 상품 소유자를 확인한다. 작가가 `albums.package_id`를 저장하면 내부값을 삭제하며, 이후 작가 선택 해제 시에도 이전 내부값은 되살아나지 않는다. RLS로 일반 작가의 내부 테이블 조회를 차단하고, 관리자 UI에 출처를 표시하며 작가 지정은 변경할 수 없게 했다. 목적 분류 및 가격 대조 스크립트도 내부 저장과 작가 우선 정책에 맞췄다.

실제 DB에서 이전 119건의 상품·가격·수정 시각이 대조 실행 당시와 동일함을 확인했다. `0117` 적용과 내부 이관을 롤백 시험한 뒤 커밋했으며, 119개 연결은 내부 테이블에 보존하고 작가용 상품·앨범 가격은 이전 실행 보고서의 원래 값으로 되돌렸다. 전체 행 해시로 목적·검수·사진·패키지 데이터 보존을 확인했다. 결과는 `scripts/embed/out/package-links/2026-09-14T17-41-54-197Z-private-migration/result.json`에 기록했다.
