작가 온보딩은 **한 번 지나면 다시 못 보는 관문들**로 이어져 있다. 입점 동의는 한 번 누르면 끝이고, 신청은 한 계정에 하나만 열린다. 눈으로 확인하려면 매번 계정을 새로 파야 했다.

`scripts/qa-photographer.cjs` 가 그 되감기를 대신한다.

## 0-A. 🎬 여기부터 — `http://localhost:3000/dev` (QA 허브)

세 입장(고객·작가·어드민)에서 흐름을 직접 눌러 보는 곳. 주소를 외울 필요가 없다.

```
node scripts/qa-seed.cjs seed     무대 세우기 — 모든 상태의 예약 8건
node scripts/qa-seed.cjs list     지금 깔린 것
node scripts/qa-seed.cjs clean    표식([QA무대]) 붙은 것만 제거
```

**무대가 없으면 어드민 큐가 안 보인다.** 「입금 확인 대기」를 보려면 입금을 알린 예약이,
「정산 대기」를 보려면 전달까지 끝난 예약이 실제로 있어야 한다. 그래서 8건을 한 번에 깐다.

| # | 상태 | 어디서 보이나 |
|---|---|---|
| ① | 작가 제안 · 수락 대기 | 고객 채팅 [수락하기] |
| ② | 수락 · 입금 전 (촬영 20일) | 고객: 계좌가 바로 열린다 |
| ③ | 수락 · 입금 전 (촬영 3일) | 고객: 계좌가 가려지고 90% 동의 모달 |
| ④ | 입금 완료 알림 | 어드민 「입금 확인 대기」 |
| ⑤ | 입금 확인됨 · 촬영 전 | 작가 [연락처 보내기]·[일정 변경] |
| ⑥ | 전달 완료 | 어드민 「정산 대기」 · 작가 정산 예정액 |
| ⑦ | 환불 신청 접수 | 어드민 접수함 [작가 합의 확인] · 거래 [환불] 잠김 |
| ⑧ | 환불 판정 끝 · 송금 전 | 어드민 「아직 송금 전」 + [송금 완료로 기록] |

### 로그인은 창을 나눈다

```
어드민 · 작가   지금 계정 그대로 (정훈 = 어드민 + 작가 김재즈)
고객            시크릿 창 → /dev/test-login → roleplay-customer@samae.test
```

같은 창에서 바꾸면 어드민 세션이 끊겨 왔다 갔다 하게 된다.

### 한 바퀴

1. 고객 창에서 채팅방 → ① 수락 → 임박 동의 → 입금 완료
2. 어드민 창 → 거래 → 「입금 확인 대기」에 뜨는가 → 입금 확인
3. 작가 시점 `/studio` → 연락처 보내기 → 고객 창에서 받기
4. 고객 창 → [사매에 문의 → 환불] → **디스코드 알림이 오는가**
5. 어드민 접수함 → [작가 합의 확인] → 거래 [환불] → [송금 완료로 기록]

⚠️ **운영 DB 에 진짜 행이 생긴다**(별도 dev 프로젝트가 없다). 메모에 `[QA무대]` 표식을
박아 두고 `clean` 이 그것만 지운다 — 실제 거래는 건드리지 않는다.

로컬이 운영 Supabase 를 그대로 쓴다(별도 dev 프로젝트가 없다). 그래서 실제 흐름을 한 번

팀 채널에 울리고, 솔라피가 문자를 쏜다(`NOTIFY_SMS_DEV=on`). 화면 보려고 스무 번 돌면
스무 번 다 그런다.

샌드박스는 그 전부를 끊는다. **나가는 네트워크 요청이 0건**이고 입력은 localStorage 에만 남는다.

```
① 안내 → ② 가입 → ③ 신청 폼 → ④ 승인 대기 → ⑤ 입점 동의 → ⑥ 완료
  /apply   카카오     /apply       어드민       /studio
```

### 🔴 약관 동의·연락처 등록은 **정규 흐름에 없다** (2026-09-15)

카카오 간편가입을 켠 뒤로 그 둘은 **카카오 동의 화면에서 한 번에** 받는다.

```
카카오 동의 화면
  ├ 서비스 이용약관   (필수)
  ├ 개인정보 처리방침 (필수)
  └ 전화번호         (선택)
       ↓
/auth/callback
  adoptKakaoServiceTerms()  → terms_agreed_at 기록 → needsTermsConsent false → /signup/consent 건너뜀
  adoptKakaoPhone()         → profiles.phone 채움  → needsContact      false → /signup/contact 건너뜀
       ↓
  next (= /apply)
```

**실제 카카오 가입자는 그 두 화면을 보지 않는다.** 정규 단계로 나열해 두면 온보딩 문서가
**없는 화면을 설명하게 된다.** 그래서 `]` `[` 가 도는 흐름에서 뺐다.

지우지는 않았다 — 아래 조건에서 진짜로 뜬다:

- **전화번호(선택 동의)를 거부한 사람** → `/signup/contact`. 실제로 자주 생긴다
- `service_terms` 조회 실패·타임아웃(4초), `KAKAO_TERMS_TAGS` 설정 오류
- **간편가입을 켜기 전에 가입한 기존 회원** → 다음 로그인에 `/signup/consent`

폴백 화면을 보려면 URL 로 직접 연다:

```
/dev/flow-auth?stage=consent&next=%2Fapply
/dev/flow-auth?stage=contact&next=%2Fapply
```

### 회원 약관도 버전을 본다 (2026-09-15 수정)

전에는 `terms_agreed_at` 이 **있는지만** 봐서 약관을 개정해도 기존 회원이 재동의하지
않았다. 작가 입점 동의는 버전 4개를 다 비교하는데(`agreementIsCurrent`) 회원 약관만
안 하고 있었다. `termsConsentIsCurrent()` 로 맞췄다 — `terms_version !== TERMS_VERSION`
이면 재동의 대상이다. 버전이 비어 있는 옛 기록도 "현재 아님" 으로 본다.

> ⚠️ `recordTermsConsent()` 에 있던 `.is("terms_agreed_at", null)` 가드도 같이 걷었다.
> 그게 있으면 **재동의를 받아도 기록이 안 남아** 매 로그인마다 같은 화면을 다시 본다.
> 대신 갱신이라 이전 동의 시각은 남지 않는다 — 버전별 이력이 필요하면
> `photographer_agreements` 처럼 행을 쌓는 표가 있어야 한다.

### 재동의도 카카오에서 받는다

카카오 계정이면 `/signup/consent` 가 **체크박스를 다시 보이지 않고 카카오로 보낸다**
(`KakaoTermsConsentButton` → `service_terms_tags`). 같은 약관을 두 군데서 받으면
"어디서 받은 동의인가" 가 갈린다. 이메일 계정만 체크박스 폼을 쓴다.

> ⚠️ **자동 리다이렉트로 만들지 않았다.** 동의를 거부하고 돌아오면 여전히 미동의라
> 또 튕기고, 또 튕긴다 — 빠져나갈 수 없는 고리가 된다. 버튼 한 번이면 그 고리가 없다.

📌 QA 계정의 `terms_version` 을 `"1.0"` 으로 박아 뒀던 걸 고쳤다. 버전 비교를 켜니
   그 계정이 매번 약관 재동의로 튕겼다 — 스크립트가 `policy-version.ts` 를 읽는다.

### 화면에 샌드박스 표시가 없다 — 이동은 키보드로

```
]  다음 단계      [  이전 단계      0  처음부터(기록 초기화)
```

전에는 상단에 단계 막대를 띄웠는데 **그게 지면을 밀어내서 실제 화면과 좌표가 달라졌다.**
QA 의 목적이 "실제와 같은 화면을 보는 것" 인데 도구가 그걸 망치고 있었다. 지금은 아무것도
그리지 않는다. 특정 단계로 바로 가려면 URL 을 쓴다.

### ② 가입의 카카오 버튼은 **진짜 카카오로 나간다**

온보딩 문서용 실제 화면을 찍어야 해서, 이 단계만 샌드박스가 가로채지 않는다.
누르면 진짜 OAuth → 카카오 동의 화면 → `/auth/callback` → `?next`(=`/apply`)로 간다.
**거기서부터는 실제 흐름이고 DB 에도 남는다.**

> 카카오 동의 화면을 보려면 먼저 [카카오계정 관리](https://accounts.kakao.com) →
> 연결된 서비스 → 사매 → **연결 끊기**. 이미 연결된 계정은 동의 화면이 안 뜬다.
> 끊어도 Supabase 계정은 그대로 남는다 — 다시 로그인하면 같은 카카오 ID 로 붙는다.

나머지 단계(약관·연락처·입점동의)는 여전히 localStorage 라 아무것도 안 남는다.

### 라우트가 둘로 갈려 있다

실제 지면들이 **서로 다른 레이아웃**에 속해 있어서다. 한 라우트에 몰면 셋 중 둘은 실제와
다른 껍데기를 쓰게 된다.

| 라우트 | 단계 | 실제 레이아웃 |
|---|---|---|
| `/dev/flow` | 안내 · 신청폼 · 승인대기 · 완료 | `(user)` — 하단 내비 + `main.pb-28` |
| `/dev/flow-auth` | 가입 · 약관 · 연락처 · 입점동의 | 레이아웃 없음(루트만) |

`]` `[` 는 두 라우트를 넘나든다 (`_flow/store.ts` 의 `stagePath`).

### 실제 지면과 대조한 결과

브라우저에서 **렌더된 DOM 텍스트**를 줄 단위로 비교했다 — 실제 `/apply`(로그인 상태) vs
`/dev/flow?stage=form`: **23줄 / 23줄, 내용·순서까지 완전 일치.**

> ⚠️ 원시 HTML 로 비교하면 순서가 다르게 보인다. 실제 지면은 Suspense 로 **스트리밍**돼서
> 바이트 순서가 다를 뿐이고(`<template>` 3개 · `$RC` 2개), 최종 DOM 은 같다.
> **원시 HTML 로 화면 일치를 판정하면 안 된다.**

폴백으로 연락처 화면을 열었을 때 인증번호는 **`000000`** 고정이다 — 실제 `ContactForm` 이
`dev 코드:` 로 스스로 보여준다(문자는 안 나간다).

마지막 화면에는 **이번 회차에 기록됐을 내용**(신청서·동의 버전·시각)이 그대로 나온다.

### 지면은 전부 실제 것이다 — 베낀 마크업이 하나도 없다

| 단계 | 그리는 것 |
|---|---|
| ① 안내 | `ApplyIntro` |
| ② 가입 | **실제 `/signup` 지면** — `AuthShell`(사진 벽) + `SignupHeadline` + `SignupForm` + `SignupFooter` |
| ③ 약관 | `ConsentBody` |
| ④ 연락처 | `ContactForm` |
| ⑤ 신청 폼 | `ApplyFormBody` |
| ⑥ 승인 대기 | `ApplyPendingBody` |
| ⑦ 입점 동의 | `AgreeGate` |
| ⑧ 완료 | 샌드박스 전용 요약 (실제엔 없는 화면) |

입력 검증도 실제 zod 스키마(`parseApplyForm`)다.

⚠️ **그래서 `/dev/flow` 는 서버 컴포넌트다.** 처음엔 클라이언트로 만들었는데, 그러면
`AuthShell`(사진 벽을 DB 에서 읽는 async 서버 컴포넌트)을 못 써서 가입 화면을 손으로
흉내 내야 했다 — **실제와 다른 화면을 QA 하게 된다.** 지금은 단계를 `?stage=` 로 받아
서버가 진짜 지면을 그리고, 상태만 클라이언트 섬이 localStorage 로 다룬다.

`?next=/apply` 도 같이 달고 다닌다. 가입 지면 표제가 **어디서 왔는지에 따라 달라져서**
(`SignupHeadline` → "작가로 시작하기"), 빼면 샌드박스만 손님용 카피를 보여준다.

실제 `/signup` 과 마크업 대조: 사진 36장·헤드라인·버튼·약관 고지·로그인 링크 전부 일치.

### 샌드박스로 못 보는 것

- 로그인·가입 화면 자체 (`/signup`·`/login` 은 밖으로 나가므로 클릭을 가로챈다)
- 어드민 승인 화면 (`/admin/photographers`) — 샌드박스는 [승인 처리하기] 버튼으로 대신한다
- 승인 뒤 프로필 탭 라벨 변화
- DB 에 실제로 뭐가 어떻게 들어가는지

**그 넷을 봐야 하면** 아래 테스트 로그인으로 실제 흐름을 탄다. 그때는 진짜로 쌓인다.

| ① 신청 전 | 신청·작가·동의 전부 없음 | **`/apply`** (로그아웃 상태로 열면 랜딩부터) |
| ② 승인 대기 | 신청 `new` | `/admin/photographers` 에서 [승인] |
| ③ 입점 동의 전 | 작가 `approved`, 동의 0건 | 프로필 탭 → **[스튜디오]** → 입점 동의 화면 |
| ④ 동의 완료 | 현재 버전 동의 기록 있음 | 프로필 탭 → [스튜디오] → 프로필 |

`setup` 은 계정을 만들고 바로 ③ 으로 열어 둔다.

### 🔴 접속은 반드시 `http://localhost:3000` — 포트까지 맞아야 한다

로그인이 깨지는 방식이 **두 가지**다. 둘 다 "계정이 잘못됐다" 처럼 보여서 엉뚱한 데를 판다.

**① IP 로 열면 이메일 로그인이 죽는다.** `192.168.0.18:3001` 같은 주소는 평문 HTTP +
비-localhost 라 보안 컨텍스트가 아니고, `window.crypto.subtle` 이 아예 없다. Supabase 의
PKCE 가 SHA-256 을 못 구해 터지는데 **화면은 그냥 로그인 페이지에 머문다.**

```
192.168.0.18:3001  →  crypto.subtle: undefined   ❌
localhost:3000     →  crypto.subtle: 있음        ✅
```

**② 포트가 3000 이 아니면 카카오 로그인이 운영 사이트로 튄다.** Supabase 의 허용
리다이렉트 목록에 `localhost:3000` 만 들어 있다. 다른 포트면 Supabase 가 Site URL 로
떨어뜨려서 **`https://samae.ai` 로 날아간다** (거기 `samae_cat` 쿠키가 있으면 `/c/wedding`
같은 데로 한 번 더 간다).

```
localhost:3000/auth/callback  →  그대로              ✅
localhost:3001/auth/callback  →  https://samae.ai    ❌
127.0.0.1:3000/auth/callback  →  그대로              ✅
```

> 3000 이 이미 물려 있으면 Next 가 조용히 3001 로 올라간다. `npm run dev` 로그의
> `Local:` 줄을 꼭 확인할 것. 3001 이면 그 프로세스를 죽이고 3000 을 비운 뒤 다시 띄운다.
> (허용 목록을 늘리려면 Supabase 대시보드 → Authentication → URL Configuration)

**이메일 가입은 꺼져 있다** (`EMAIL_SIGNUP_ENABLED = false`, docs/15 — SMTP 준비 전).
그래서 `/signup` 은 카카오만 보인다. 의도된 상태지 고장이 아니다.

## 1-1. 작가 진입로 — 뿌리는 주소는 `/apply` 하나다

```
   https://samae.ai/apply          ← 작가에게 뿌리는 주소. 로그인 없이 열린다
        │
        ├─ 비로그인 → 안내 지면(무엇을 하는 곳인지·3단계·수수료 링크)
        │      └ [작가 신청 시작하기] → /signup?next=/apply
        │      └ [이미 계정이 있어요] → /login?next=/apply
        │             └ 가입·로그인 끝나면 **다시 /apply** 로 돌아온다
        │
        ├─ 로그인 + 작가 아님 → 신청 폼 (작가명·포트폴리오·연락처)
        ├─ 로그인 + 신청 대기 → 승인 대기 화면
        └─ 로그인 + 작가     → /studio 로 보냄

   폼 제출 → photographer_applications (new)
        └ 어드민 /admin/photographers → [승인]
             └ photographers (approved) 생성
                  └ 프로필 탭에 [스튜디오] 가 생긴다
                       └ 들어가면 입점 동의 화면
```

### 프로필 탭에는 [작가 신청] 이 없다 (2026-09-15 결정)

예전에는 가입한 뒤 **프로필 메뉴를 뒤져야** 신청 버튼이 나왔다. 링크 하나로 끝날 일이
세 단계였다. 모집은 `/apply` 링크를 직접 뿌리는 방식으로 가기로 하고, 프로필 탭의
[작가 신청] 은 뺐다 (`ProfileSheet.tsx`).

**두 진입로를 다 두지 않는 이유** — 문구·조건·추적을 두 군데서 맞춰야 하고, 한쪽만
고치면 조용히 어긋난다. 손님의 99%는 작가가 될 생각이 없으니 일반 회원 메뉴가
가벼워지는 것도 덤이다.

프로필 탭에 남는 건 작가에게만 보이는 **[스튜디오]** 뿐이다 (`me.isPhotographer`).

> ⚠️ **`/studio` 로 직행해서 QA 하지 말 것.** 승인된 작가는 프로필 탭을 통해 들어온다.
> 직행하면 라벨 등장·신청 폼·승인 대기 화면을 통째로 건너뛴다.

> 📌 `/studio` 에 남아 있는 "작가 신청하기" 카드는 **주소를 직접 친 사람을 위한 복구
> 경로**다. UI 상의 진입로가 아니다.

## 2. 관문이 열리고 닫히는 조건

게이트는 `src/app/(photographer)/studio/layout.tsx` 가 잡는다. 판정은 딱 하나다 —

> `photographer_agreements` 의 **최신 행** `versions` 가 현재 버전과 **전부** 같은가
> (`lib/consent.ts` → `agreementIsCurrent`)

```
terms    PHOTOGRAPHER_TERMS_VERSION      1.0
fee      FEE_POLICY_VERSION              1.0
refund   REFUND_POLICY_VERSION           1.0
contract PHOTOGRAPHER_CONTRACT_VERSION   2.0
```

따라서 **네 중 하나라도 버전이 올라가면 전 작가가 다시 동의 화면을 본다.** 정책 문서를 고칠 때 버전을 올릴지 말지가 곧 "재동의를 받을지"의 결정이다.

`profile` 단계는 `policy-version.ts` 를 **읽어서** 심는다 — 상수를 스크립트에 복제하지 않았다. 복제하면 버전이 올라갈 때 조용히 어긋난다.

## 3. 입점 동의 화면에서 볼 것

프로필 탭 → [스튜디오] 로 들어가면 뜨는 `AgreeGate` 의 구성:

1. **꼭 알아야 할 것** — 수수료율·정산 시점·작가 귀책 취소·오프플랫폼 금지·연락처 파기 (약관규제법 3조 설명 의무)
2. **문서 동의 (필수)** — 체크박스 4개, 각각 새 탭 링크 + 버전 표기
   - 작가 입점 계약 `/terms/photographer-contract`
   - 작가 이용약관 `/terms/photographer`
   - 수수료·정산 정책 `/terms/fees`
   - 취소·환불 정책 `/terms/refund`
3. **작가 정보 (계약 당사자)** — 성명/상호 · 사업자 유형 · 사업자등록번호
4. **홍보 사용 동의 (선택)** — 입점계약 7조

### 🔴 아직 안 된 것 — 이번 QA 의 주 대상

- **[모두 동의] 버튼이 있다.** 네 문서를 한 번에 체크한다. "전부 읽고 동의" 와 정면으로 어긋난다
- **문서를 안 열어도 동의가 된다.** 링크는 새 탭일 뿐, 열었는지 읽었는지 확인하지 않는다
- **전용 열람 페이지가 없다.** 흐름 안에서 끝까지 스크롤해야 동의가 열리는 지면이 필요하다
- **동의 기록에 문서별 열람·동의 시각이 없다.** 지금은 `versions` 묶음 하나 + `agreed_at` 하나뿐이라, "어느 문서를 언제 읽고 언제 동의했는가" 를 문서별로 주장할 수 없다
- **주민등록번호(§3-4)** 미구현 — 사업자 미등록 작가의 3.3% 원천징수 대상

- [ ] 승인 직후 프로필 탭에 [스튜디오] 가 생기는가
- [ ] 그 [스튜디오] 가 곧장 동의 화면으로 가는가

## 4-1. 💰 결제·정산 샌드박스 (2026-09-15 추가)

돈이 걸린 화면은 실제 예약으로 QA 하기가 나쁘다. 임박 예약을 만들려면 촬영일이 3일 뒤인
예약을 실제로 잡아야 하고, 원천징수를 보려면 작가 계정을 둘 만들거나 DB 를 직접 고쳐야 한다.
그래서 **화면만 떼어 놓은 주소 두 개**를 뒀다. 온보딩 샌드박스(§0-0)와 같은 원칙이다 —
지면은 실제 컴포넌트 그대로이고, **데이터와 서버 액션만 갈아 끼운다. 밖으로 나가는 게 없다.**

### `/dev/chat` — **여기가 실제 자리다** (`]` `[` 로 이동)

예약은 채팅 안에서 협의하고 제안하고 수락한다. 결제 팝업은 **수락하는 그 순간** 뜬다.
아래 `/dev/pay` 는 그 팝업만 떼어 본 것이고, 순서대로 보려면 이쪽이다.

| 단계 | 주소 | 볼 것 |
|---|---|---|
| ① 임박(3일) 제안 도착 | `?stage=late` | [수락하기] → **위약금 동의 모달이 먼저** 선다 |
| ② 여유(20일) 제안 도착 | `?stage=normal` | [수락하기] → 동의 없이 바로 계좌·위약금 표 |
| ③ 수락만 하고 나갔다 돌아온 방 | `?stage=revisit` | 방에 들어오자마자 **자동으로 다시 뜨는가** (`pendingPay`) |
| ④ 입금 완료 누른 뒤 | `?stage=marked` | 팝업이 안 뜨고 카드가 「수락됨 · 입금 대기」인가 |
| ⑤ 입금 확인됨 | `?stage=paid` | 연락처 전달 · 일정 변경. **`r` 로 고객↔작가 전환** |

방은 실제 `ChatRoom` · `ChatShell` 이다. 갈아 끼우는 건 메시지·예약과 `ChatIO`(chat-io.ts)
뿐이라 **DB 쓰기·실시간 구독·Mixpanel 이 전부 끊긴다.**

**⑤ 는 눌러서 진행된다.** 스텁이 no-op 이 아니라 예약 스냅샷을 고치기 때문이다 —
실제 컴포넌트들이 액션 뒤에 `router.refresh()` 를 부르는데, 서버가 같은 고정값을 다시
내려주면 화면이 한 발짝도 안 나간다.

⚠️ **역할 전환은 `r` 이지 주소가 아니다.** 연락처 전달은 작가가 보내고 고객이 받는 두 사람의
일인데, 역할을 단계로 나누면 옮기는 순간 방이 새로 마운트돼 **보낸 사실이 사라진다.**
`r` 은 같은 방의 시점만 바꾸므로 눌러 둔 상태가 그대로 남는다.

- **연락처** (docs/32 §3-3): `r`로 작가 → [연락처 보내기] → 타임라인에 카드가 선다 →
  `r`로 고객 → **용도 제한 고지를 읽고** [연락처 받기] → 전화번호·인스타가 펼쳐진다.
  볼 것은 **받기 전에 고지가 뜨는가** — 받은 뒤에 알리면 고지가 아니라 통보다
- **일정 변경** (취소환불 7조): 어느 쪽에서든 [일정 변경 요청] → 새 일시 입력 →
  `r`로 상대 시점 → 카드에서 [동의해요]. 동의하면 촬영일이 바뀌고
  **환불 기준도 새 날짜로 다시 계산된다**

단계(`]` `[`)를 옮기면 눌러 둔 상태는 초기화된다 — `page.tsx` 가 `key` 로 새로 마운트한다.

⚠️ **예약서 작성기는 열리지 않는다.** 제안은 서버에 쓰는 동작이라 샌드박스가 흉내 낼 수
없다 — 그래서 이미 제안된 상태로 시작한다. 제안 자체를 QA 하려면 실제 계정 두 개가 필요하다.

### `/dev/pay` — 결제 게이트만 떼어 보기 (`]` `[` 로 이동)

`/bookings/[id]` 의 입금 구간이다. 알림 링크가 전부 이쪽이라 **채팅을 거치지 않고도
결제가 가능한 두 번째 경로**고, 2026-09-15 까지 여기만 게이트가 비어 있었다.

| 단계 | 주소 | 볼 것 |
|---|---|---|
| ① 임박·동의 전 | `?stage=late` | **계좌가 가려지는가.** 번호가 먼저 보이면 동의 전에 송금해 버린다 |
| ② 임박·동의 후 | `?stage=late-agreed` | 위약금 90% 문구로 바뀌는가, 체크 문구도 같이 바뀌는가 |
| ③ 여유 예약 | `?stage=normal` | 전액 환불 마감일·40%·90% 가 **날짜로** 박히는가 |
| ④ 입금 완료 후 | `?stage=paid` | 버튼이 사라지고 결과 문구만 남는가 |

`(user)` 레이아웃 안에 두어 하단 내비까지 같게 만들었다 — 루트에 두면 껍데기가 달라진다.

### `/dev/money` — 정산 금액

`?type=unregistered` 와 `?type=general` 을 오간다. 상단 막대만 샌드박스 장치고,
아래 두 지면은 실제 컴포넌트다(`SettlementsBody` · `BookingMoney`).

- [ ] 미등록: 원천징수 안내 블록과 각 행의 `원천징수 ₩…` 가 뜨는가
- [ ] 일반과세자: 그 둘이 **전부 사라지는가**
- [ ] 3만원 건에는 원천징수가 0 인가 (소액부징수 — 소득세 900원 < 1,000원)
- [ ] 어드민 금액: 대금 − 수수료 − 부가세 − 원천징수 가 「작가 송금액」과 맞는가

금액은 손으로 적지 않고 `resolveFee` · `computeWithholding` 을 돌려 만든다. 계산이 바뀌면
이 화면도 같이 바뀐다 — 안 그러면 샌드박스가 옛 숫자로 거짓말을 한다.

### 여기서 못 보는 것

- **스튜디오 좌측 사이드바**(`studio/layout`)와 **어드민 상단 껍데기**. 둘 다 로그인·권한을
  요구하는 서버 레이아웃이라 끌고 올 수 없다. 여기서 보는 건 숫자와 문구다
- **예약서 제안·메시지 전송** — 서버에 쓰는 동작이라 전부 끊어 뒀다
- 실제 저장 — 동의 시각도 입금 표시도 남지 않는다. DB 에 남는지는 실제 계정으로 확인한다.
