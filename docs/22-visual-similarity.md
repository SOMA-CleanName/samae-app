## 1. 배경 / 문제

사진 상세 하단 **"이런 사진은 어때요?"** 는 현재 태그 겹침으로 계산한다.

1. `photos` 에서 **최신순 400장**을 가져온다.
2. 현재 사진의 `mood_tags` 와 겹치는 태그 **개수**로 점수를 매긴다.
3. 같은 앨범을 제외하고, 점수 묶음 안에서 앨범별 라운드로빈 + `spaceByAlbum` 으로 분산한다.

**한계**

1. **후보가 최신 400장뿐이다.** 공개 사진이 1,572장이므로 **72%는 후보에 들어오지도 못한다.** 오래된 사진일수록 영원히 추천되지 않는다.
2. **태그가 유사도를 대신하지 못한다.** `mood_tags` 는 작가 수기 입력이라 사람마다 어휘가 다르고, 태그가 비어 있으면 점수가 전부 0이 되어 사실상 무작위 정렬이 된다.
3. **같은 태그 ≠ 같은 무드.** "감성"이라는 같은 태그를 단 사진이라도 톤과 분위기가 전혀 다를 수 있다.

**원하는 것**: 사진을 클릭하면 **사람이 봐도 비슷한 감성의 사진**이 뜬다. 태그 유무·등록 시점과 무관하게 전체 공개 사진이 후보가 된다.

관련 코드:

- `src/lib/discovery.ts` — `fetchSimilarPhotos()`
- `src/app/(user)/photos/[id]/page.tsx` — `Recommendations`

## 2. 목표 / 비목표

**목표**

- 공개 사진 전체를 이미지 임베딩으로 색인하고, 사진→사진 근접검색으로 추천을 계산한다.

## 4. 모델 결정

### 4.1 선택

```
google/siglip2-so400m-patch16-naflex
```

- 임베딩 차원: **1152**
- 라이선스·비용: 구글이 공개한 오픈 웨이트. **다운로드·사용 무료, 호출 과금 없음.** (OpenAI/Gemini 임베딩 API 와 다르다)

### 4.2 왜 naflex 인가

일반 SigLIP 2 체크포인트(`patch14-384` 등)는 입력을 **정사각으로 리사이즈**한다. §3에서 확인했듯 공개 사진의 80.6%가 세로라, 정사각 입력은 대다수 사진의 구도와 여백을 왜곡한다. 인물 스냅에서 구도는 무드의 핵심 요소다.

naflex 변형은 **원본 종횡비를 유지**한 채 가변 길이 패치 시퀀스로 처리한다. 세로·가로가 섞인 카탈로그에 맞는 형태다.

### 4.3 왜 모델 크기를 더 고민하지 않았는가

임베딩은 **오프라인 배치로만** 계산한다(§5). 조회 시점에 모델이 돌지 않으므로 모델 크기가 서비스 응답 속도나 상시 비용에 영향을 주지 않는다. so400m 과 base 의 실질 차이는 백필 1회 소요 시간뿐인데, 실측 결과 so400m 조차 1,572장에 **1~4분**이라(§4.4) 더 작은 모델로 아낄 것이 없다.

### 4.4 `max_num_patches` (해상도 예산)

naflex 는 입력 패치 수 상한(`max_num_patches`)이 사실상 해상도 예산이다. 인자명·기본값은 확인했고, 2:3 사진(500×750 thumb) 기준 입력 크기는 실측했다.

| `max_num_patches` | 실제 입력 (실측) | 300장 임베딩 | thumb 으로 가능? |
|---|---|---|---|
| **256** (기본값) | 13×19 패치 = **208 × 304** | 12초 | 가능 |
| **1024** | 26×39 패치 = **416 × 624** | 48초 | 가능 |
| 2048 | 약 591 × 886 | — | 불가 — `src_url` 필요 |

**1024까지는 thumb 으로 커버된다.** 두 설정의 top-10 일치율은 69.4% 로 30%는 다른 사진이 나오지만, 육안 비교에서 우열이 갈리지 않았다.

**결정: `max_num_patches = 256`.** 근거:

| 지표 | 256 | 1024 |
|---|---|---|
| 시드와 명도 차이 | **0.1489** | 0.1571 |
| 시드와 채도 차이 | **0.1307** | 0.1389 |
| top-8 중 같은 작가 | **39.9%** | 42.1% |
| top-8 등장 작가 수 | **3.3명** | 3.2명 |
| 변별폭(top1 − 전체평균) | 0.214 | **0.229** |

톤 일관성과 작가 다양성에서 256 이 모두 앞선다. 1024 가 앞선 변별폭은 유사도 점수가 더 벌어진다는 뜻일 뿐 품질 지표가 아니다. 여기에 256 은 모델 기본값이고 4배 빠르다. **근거 없이 기본값을 벗어나지 않는다**는 원칙에 따라 256 으로 간다.

전환 비용이 낮으므로(§9.3) 이 결정은 잠금이 아니다. 사진이 늘어 두 설정이 갈리기 시작하면 그때 재평가한다.

### 4.5 구현 함정 두 가지

각 스크립트가 따로 구현하면 하나는 반드시 틀리게 짜고, **틀려도 에러 없이 그럴듯한 벡터가 나와** 발견이 늦는다. 그래서 `scripts/embed/siglip.py` 에 모아두고 전부 그것만 쓴다.

**함정 1 — NaFlex 는 입력 텐서가 3개다.**
`pixel_values` 외에 `pixel_attention_mask`(패딩 마스크)와 `spatial_shapes`(원본 비율)를 함께 넘겨야 한다. 비율이 제각각이라 배치 안에서 패딩이 생기고 그것을 모델에 알려줘야 한다. processor 결과를 통째로 언팩(`**inputs`)하면 자연히 지켜진다.

**함정 2 — `get_image_features` 가 텐서를 반환하지 않는다.**
transformers 5.x 에서 이 메서드는 `vision_model` 의 출력 객체(`BaseModelOutputWithPooling`)를 그대로 돌려준다. **공식 docstring 예제조차 텐서처럼 쓰고 있어 그대로 믿으면 틀린다.** 풀링 벡터는 `pooler_output` 이며, `last_hidden_state` 는 패치별 토큰이라 사진 단위 유사도에 쓰면 안 된다.

추가로 `torchvision` 이 없으면 `Siglip2ImageProcessor` 가 **경고 한 줄만 남기고 PIL 폴백으로 갈아탄다.** 리사이즈 결과가 달라져 평가와 백필의 임베딩이 어긋나므로 `requirements.txt` 에 명시해 고정한다.

### 4.6 알려진 한계

SigLIP 계열 임베딩은 **피사체·상황(의미)이 지배적**이고 톤·질감 표현은 상대적으로 약하다. "노을 아래 커플" 을 넣으면 노을 커플도 나오지만 그냥 커플도 섞여 나온다.

5단계 결과가 "무드가 아니라 피사체만 맞는다" 로 판정되면 7단계(톤 디스크립터 가중 합산)를 진행한다.

> **판정 (2026-08-08): 무드가 잘 맞는다. 7단계는 착수하지 않는다.**
>
> 5단계 배포 후 실제 추천을 보고 내린 판단이다. 위에 적어둔 실패 모드("피사체만 맞는다")가 관찰되지 않았으므로, 그것을 겨눈 처방인 7단계는 겨눌 대상이 없다. 그럼에도 톤 가중치를 시험해봤고 그 결과는 §7.6 에 남겼다. **재검토 조건도 §7.6 에 있다.**

## 5. 아키텍처

```
[업로드된 사진]
      │
      │  (오프라인 배치 · Python)
      ▼
  SigLIP 2 naflex  ──►  1152차원 벡터  ──►  photos.embedding (halfvec)
                                                    │
                                                    │  HNSW 인덱스
[사용자가 사진 클릭]                                 ▼
      │                                      코사인 근접검색 (SQL)
      └────────────────────────────────────────────┤
                                                    ▼
                                        앨범 분산 후처리 → 추천 그리드
```

### 5.1 핵심 성질 — 조회 시점 추론이 없다

사진→사진 추천은 **클릭된 사진이 이미 자기 벡터를 갖고 있으므로** 요청 시점에 모델을 돌릴 필요가 없다. SQL 근접검색 한 번으로 끝난다.

결과적으로:

- 추가 응답 지연 **없음**
- 추론 서버·GPU **불필요** (Vercel 서버리스에 torch 를 올릴 필요가 없다)
- 트래픽이 늘어도 **추론 비용이 늘지 않음**

Python 은 앱에 들어오지 않는다. 배치 스크립트로만 존재한다.

### 5.2 왜 FAISS 가 아니라 pgvector 인가

| 기준 | pgvector | FAISS |
|------|----------|-------|
| 노출 규칙(`published` + `approved`) | SQL 조인으로 자연스럽게 적용 | 인덱스가 모름 → 앱에서 재구현 필요 (사고 지점) |
| 운영 | Supabase 안에 포함 | Vercel 밖에 상태를 가진 서비스 추가 운영 |
| 규모 | HNSW 로 수백만 행 처리 가능 | — |

현 규모에서 FAISS 의 이점은 없고 리스크만 있다.

## 6. 데이터 모델

이 과제가 만든 마이그레이션은 둘이다. 둘 다 `photos` 에 컬럼을 **추가만** 하며 기존 컬럼·데이터·RLS 를 건드리지 않는다.

| | 컬럼 | 쓰이는 곳 |
|---|---|---|
| `0068_photo_embeddings.sql` | `embedding` · `embedding_model` · `embedded_at` | **사용 중** — 사진 상세 추천(§7.2) |
| `0074_photo_auto_mood_tags.sql` | `auto_mood_tags` · `auto_mood_model` · `auto_mood_at` | **읽는 코드 없음** (§7.5) |

아래는 `0068` 기준이다. `0074` 는 §7.5 참조.

| 컬럼 | 타입 | 용도 |
|------|------|------|
| `embedding` | `extensions.halfvec(1152)` | 이미지 임베딩 |
| `embedding_model` | `text` | 생성에 쓴 모델 식별자 |
| `embedded_at` | `timestamptz` | `null` = 배치 대상 |

**`halfvec` 인 이유**: 차원당 2바이트. 1,572장 기준 약 3.5MB(`vector` 는 7MB). 검색 품질 차이는 없다.

**`embedding_model` 이 있는 이유**: 모델을 교체할 때 어떤 사진이 구 모델 벡터인지 구분해 **점진 재계산**을 할 수 있다. 이 컬럼이 없으면 전량 재백필 외에 방법이 없다.

**값 형식은 `<모델명>@<max_num_patches>`** 로 고정한다.

```
siglip2-so400m-patch16-naflex@256
```

모델명만 기록하면 해상도 설정이 남지 않아 "이 행은 256인가 1024인가"를 알 수 없고, 컬럼을 둔 목적이 반쪽이 된다. 이 형식이면 `where embedding_model <> '...@1024'` 로 재계산 대상만 고를 수 있다.

**인덱스 2개**

- `idx_photos_embedding_hnsw` — HNSW 코사인. `where visibility = 'published'` 부분 인덱스.
  `photographers.status='approved'` 는 다른 테이블이라 인덱스 조건에 넣을 수 없다. HNSW 로 넉넉히 뽑고 바깥 조인에서 거른다(4단계 RPC).
- `idx_photos_embedding_pending` — 배치 대상 큐. `0047` 의 `idx_photos_tag_generation_pending` 과 동일한 패턴.

### 6.1 search_path 주의

pgvector 타입·연산자는 **`extensions` 스키마**에 설치된다. Supabase 는 `public` 을 PostgREST 로 외부 노출하므로 확장을 `public` 에 넣지 않는 것이 관례다.

문제는 기존 RPC 들이 `set search_path = public` 으로 고정돼 있다는 점이다(`feed_photos_taste` 등). **이 상태로 함수 안에서 `<=>` 연산자를 쓰면 `operator does not exist` 에러가 난다.**

따라서:

- 컬럼·인덱스 정의: `extensions.halfvec(1152)`, `extensions.halfvec_cosine_ops` 로 **스키마 한정** (`0068` 에 반영 완료)
- 4단계 RPC: `set search_path = public, extensions`

### 6.2 현재 규모에서는 플래너가 HNSW 를 쓰지 않는다 (정상)

2026-08-06 실측. 공개 사진 1,582장 기준으로 실행계획을 보면 `Seq Scan` 이 선택된다. **쿼리가 잘못된 것이 아니라 플래너의 정당한 판단이다.**

`set enable_seqscan = off` 로 강제하면 인덱스를 정상적으로 탄다.

| | Seq Scan (기본 선택) | HNSW (강제) |
|---|---|---|
| 플래너 추정 비용 | 281.39..**282.14** | 160.74..**290.81** |
| 읽은 버퍼 | 9,712 | **735** |
| 실행 시간 | 235ms | 222ms |

전체 1,514행 중 300행(약 20%)을 가져오는 상황이라, 전부 읽고 top-N 정렬하는 비용과 HNSW 그래프를 `ef_search=400` 으로 순회하는 비용이 거의 같다(282 vs 291). 데이터가 늘면 Seq Scan 은 행 수에 비례해 비싸지고 HNSW 는 로그 스케일이므로 **자동으로 인덱스 쪽으로 넘어간다. 손댈 것이 없다.**

읽은 버퍼가 13배 차이 나는데 시간이 비슷한 것은 현재 전 데이터가 메모리에 올라와 있기 때문이다. 테이블이 캐시를 넘어서면 이 차이가 그대로 지연으로 드러난다.

> 실제 RPC 왕복 지연은 **89ms**(네트워크 포함, 12회 중앙값)다. 위 `explain analyze` 의 222ms 에는 계측 오버헤드가 포함돼 있어 사용자 체감과 다르다.

**점검 방법** — 나중에 느려졌다고 느끼면 위 `enable_seqscan` 비교를 다시 돌려 인덱스가 여전히 사용 가능한지부터 본다. `reset enable_seqscan;` 을 반드시 함께 실행할 것.

### 6.3 HNSW `ef_search` — 함수 SET 절에 넣을 수 없다

`hnsw.ef_search` 는 HNSW 의 탐색 폭이며 **기본값이 40** 이다. 이 값이 조회 `limit` 보다 작으면 pgvector 가 요청한 만큼 돌려주지 못한다. 4단계 RPC 는 후보를 300장 뽑으므로 기본값 그대로면 40장 남짓만 오고, 승인작가·같은게시물 필터를 거친 뒤에는 최종 개수가 모자란다. **에러가 아니라 추천이 빈약해지는 형태로만 드러나므로 발견이 늦다.**

그런데 이 값을 함수 헤더에 둘 수 없다.

```sql
create function ... 
set hnsw.ef_search = 400   -- ERROR 42501: permission denied to set parameter
```

`CREATE FUNCTION ... SET` 은 **정의 시점에** 파라미터 이름을 검증한다. 그 시점의 세션에는 pgvector 라이브러리가 로드돼 있지 않아 Postgres 가 `hnsw.ef_search` 를 정체불명의 placeholder 로 판단하고, **placeholder 설정은 superuser 전용**이다. Supabase 의 `postgres` 롤은 superuser 가 아니다.

**해법 — 본문에서 실행 시점에 건다.**

```sql
-- 위에서 이미 p.embedding 을 읽어 pgvector 가 로드된 뒤라 여기서는 통과한다.
perform set_config('hnsw.ef_search', greatest(v_pool, 100)::text, true);
```

세 번째 인자 `true` 는 **트랜잭션 한정**이다. Supabase 는 커넥션 풀을 쓰므로 이것이 없으면 설정이 커넥션에 남아 다른 요청에 영향을 준다.

후보 풀 크기(`v_pool`)에서 계산하므로 `p_limit` 을 키워도 따로 손볼 필요가 없다.

> **현재 유효한 함수 정의는 `0069` 가 아니다 (2026-08-08).** PR #268 의 `0074_photo_feed_hidden.sql` 이 `create or replace` 로 다시 만들며 후보 풀에 `and not p.feed_hidden` 을 추가했다(위 `v_pool` 과 같은 이유로 바깥이 아니라 풀 안이다). 이 절의 `set_config`·`search_path` 처리는 그대로다. **이 함수를 손볼 때는 그 파일에서 출발할 것.**

5단계가 배포된 지금도 같은 성질이 유지된다. 남은 6~8단계는 **착수하지 않아도 현재 추천이 그대로 동작한다.** 6단계 없이도 신규 사진은 태그 폴백으로 뜨고(§7.2), 7·8단계는 추천 품질을 더 올리려는 것이지 지금 것을 고치는 게 아니다.

> **7·8단계에서 배운 것 — 증상 없는 처방은 하지 않는다.**
>
> 둘 다 "이렇게 하면 더 좋아질 것" 이라는 계획으로 문서에 적혀 있었고, 둘 다 실측해보니 **고칠 문제가 없었다.** 7단계는 무드가 이미 잘 맞았고(§4.6), 8단계는 겨눴던 수혜자가 아예 없어졌다(§7.5).
>
> 두 번 다 **오프라인 검증을 먼저 하고 DB·앱을 나중에 건드린 덕에** 접는 비용이 0 이었다. 8단계에서 만든 컬럼(`0074`)조차 읽는 코드가 없어 위험이 없다. **이 순서를 지킬 것** — 하네스 → 측정 → 판정 → 그다음에 스키마.
>
> 반대로 잘못한 것도 기록해둔다. 8단계는 전제가 무너진 뒤에도 "다른 소비처를 찾자" 로 계속 진행했다. **전제가 깨지면 그 자리에서 멈추고 되물었어야 했다.**

### 7.1 1단계 — 평가 하네스

**모델을 DB에 붙이기 전에 오프라인으로 먼저 고른다.** 이 단계를 건너뛰면 "좋아진 건지 모르는" 상태로 전 과정을 진행하게 된다.

시드 사진과 그 top-10 을 나란히 렌더한 HTML 을 눈으로 비교한다. 정답 라벨이 없으므로 자동 지표(mAP 등)는 만들지 않는다.

```bash
scripts/embed/.venv/bin/python scripts/embed/fetch_sample.py --limit 300
scripts/embed/.venv/bin/python scripts/embed/eval_models.py --budget 256
scripts/embed/.venv/bin/python scripts/embed/eval_models.py --budget 1024
# → scripts/embed/out/*.html 두 개를 나란히 열어 비교
```

**표본 구성** (2026-08-05): 공개 사진 1,000장 풀에서 등간격 추출한 300장 · 게시물 106개 · 작가 10명. 등간격이라 재실행해도 같은 표본이 나온다.

**부수 지표 — top-10 중 같은 게시물 비중**: `budget=256` 에서 21.3%, `1024` 에서 23.3%. 벡터 추천이 같은 촬영본을 상위에 몰아넣는 정도이며, 앨범 분산 후처리(§7.2)의 필요도를 나타낸다. 다만 표본의 작가가 10명뿐이라 실제보다 높게 잡힐 수 있다.

이 하네스는 7단계 검토에서 그대로 재사용했다 — `eval_tone.py` 가 여기서 만든 임베딩 캐시를 읽는다(§7.6).

### 7.2 5단계 — 교체 결과

`fetchSimilarPhotos` 에서 **점수 계산만** 바꾸고 나머지는 그대로 뒀다. 호출부(`page.tsx`)와 반환 타입(`SimilarPhoto`)은 건드리지 않았다.

- `similarByTags` — 기존 `mood_tags` 겹침. 폴백으로 보존

### 7.3 근접중복 사진이 나란히 뜬다 — 확인된 이슈, 조치하지 않음

**증상**: 사진 상세 추천에 **눈으로 보기에 완전히 같은 사진이 연달아** 나올 수 있다.

**원인은 코드가 아니라 데이터다.** 같은 작가가 동일한 이미지를 서로 다른 게시물에 각각 올린 경우다. 업로드마다 Storage 경로(uuid)가 새로 생기므로 `src_url` 이 달라 DB 상으로는 완전히 별개의 행이고, 시스템이 중복임을 알 방법이 없다.

**실측 (2026-08-06, 공개 1,582장 전수 임베딩 비교)**

| 코사인 유사도 | 쌍 수 | 같은 게시물 | 다른 게시물 |
|---|---|---|---|
| > 0.99 | 7 | 4 | **3** |
| > 0.98 | 16 | 13 | **3** |
| > 0.95 | 214 | 210 | **4** |

문제가 되는 것은 **다른 게시물인 3쌍**이다. `cos ≈ 1.0001` 로 사실상 픽셀 단위로 같은 이미지이며, 세 쌍 모두 **같은 작가**가 올린 것이다. 같은 게시물인 쌍은 RPC 가 이미 제외하므로 화면에 나오지 않는다.

**왜 지금 드러났나.** 기존 태그 방식에서는 두 장의 점수가 같아도 셔플되어 멀리 떨어졌다. 벡터는 거리가 0 이라 **반드시 연달아 나온다.** 없던 문제가 생긴 것이 아니라 원래 있던 데이터 중복이 가시화된 것이다.

`spaceByAlbum` 도 막지 못한다. 그것은 **같은 앨범**끼리만 떼어놓는데, 이 쌍들은 앨범이 다르다.

**조치하지 않기로 한다.** 1,582장 중 3쌍이고, 해당 사진을 클릭했을 때만 드러난다. 작가가 같은 사진을 여러 게시물에 올리는 것(예: 서로 다른 패키지 소개) 자체는 정당할 수 있어 금지할 근거가 없다.

**검토했으나 채택하지 않은 대안**

- *앱에서 근접중복 접기* — `similarByEmbedding` 에서 `distance < 0.01` 인 것을 첫 장만 남긴다. 코드 몇 줄이고 앞으로 생길 중복도 자동 처리된다. 빈도가 늘면 이 방법으로 간다.
- *데이터 정리* — 운영이 중복 행을 삭제한다. 근본적이지만 운영 부담이 있고 재발한다.

**재발 시 판단 기준**: 위 전수 비교를 다시 돌려 **다른 게시물 쌍이 두 자릿수**가 되면 앱 단 접기를 도입한다. 정상적인 "비슷한 사진" 의 유사도는 0.87~0.91 이므로, 임계값 0.99 는 정상 추천에 전혀 영향을 주지 않는다.

### 7.4 6단계 — 신규 업로드 처리 (의도적 보류)

Vercel 서버리스에 torch 를 올릴 수 없어 신규 사진 임베딩에는 별도 경로가 필요하다. **당분간 3단계 배치를 주 1회 수동 실행한다.**

근거: `generated_tags` 도 동일한 방식(주간 배치 + 어드민 검수)으로 운영 중이고, 현재 업로드량에서는 신규 사진이 며칠 추천에 안 뜨는 것이 인프라를 추가할 값어치가 없다. **비용 0, 새 실패 지점 0.**

**보류의 대가**: 임베딩이 없는 사진은 자기 상세에서 태그 폴백으로 떨어지는 데 그치지 않는다. `0069` RPC 의 후보 조회에 `embedding is not null` 이 있어 **다른 사진의 추천에도 등장하지 못한다.** 폴백이 가려주는 것은 절반뿐이므로, 배치를 거르면 그만큼 카탈로그가 추천에서 사라진다.

**자동화 전환 조건** (둘 중 하나면 착수)

- 업로드가 하루 100장을 넘음
- 작가가 "새 사진이 추천에 안 뜬다" 고 문의하기 시작함

> **관찰 (2026-08-07)**: 08-06 백필 이후 하루 만에 대기가 **181장** 쌓였다. 위 임계값을 넘지만 하루치 한 번은 추세가 아니고, 이 수치에는 신규 업로드뿐 아니라 비공개→공개 전환분도 섞여 있다(§9.2). **다음 주 배치에서 다시 100장을 넘으면 6단계를 착수한다.**

**전환 시 형태**: Modal 또는 HF Inference Endpoint 에 임베딩 함수를 올리고, 크론 라우트가 pending 큐를 읽어 호출한다. 인증은 기존 `daily-digest` 의 `CRON_SECRET` Bearer 패턴을 따른다.

관련 코드:

- `src/app/api/cron/daily-digest/route.ts` — 크론 인증 패턴의 원본
- `vercel.json` — 크론 등록

### 7.5 8단계 — 무드 태그 자동 생성 (태그는 생성함 · 소비처는 연결하지 않음)

**결론부터.** 무드 어휘 45개를 만들어 공개 사진 1,763장에 `auto_mood_tags` 를 붙였다(2026-08-08). 그러나 **읽는 코드는 만들지 않았다.** 원래 겨눴던 수혜자가 실측 결과 존재하지 않았고, 대안 수혜자도 증상이 없었기 때문이다. 사용자 화면은 전혀 바뀌지 않았다.

이 절은 **왜 만들었고 왜 연결하지 않았는지**를 남긴다. 다음 사람이 같은 조사를 반복하지 않게 하는 것이 목적이다.

#### 원래 계획과 그 전제

> 작가 수기 `mood_tags` 는 커버리지가 얇다 → SigLIP 텍스트 타워로 무드 태그를 자동 생성한다 → **취향 피드(`feed_photos_taste`)의 랭킹이 좋아진다**

SigLIP 2 는 이미지와 텍스트를 같은 공간에서 다루므로, 무드 어휘를 텍스트 타워로 임베딩해 사진 벡터와의 유사도로 태그를 붙일 수 있다. 기술적으로는 성립한다. 문제는 전제였다.

#### 전제 검증 — 네 개 중 네 개가 어긋났다 (2026-08-08 실측)

#### `generated_tags` 의 정체 (조사 결과)

새 컬럼을 만든 이유이므로 남긴다. 이 컬럼은 정교한 AI 산출물이 **아니다.**

```
tag_generated_at 채워진 사진   828장
생성 시각                     2026-06-22 하루에 전부
tag_reviewed = true             0장          ← 검수된 적 없음
게시물(앨범) 82개 중 앨범 내 전 사진 동일 태그  81개 (99%)
고유 태그 조합                  70개
```

**사진 단위가 아니라 게시물 단위로 붙었다.** 828장에 조합이 70개뿐이고 앨범 하나당 조합 하나다. 이미지를 한 장씩 본 결과라면 이렇게 될 수 없다. 내용도 `서울 전지역`·`핀터레스트`·`프로필`처럼 이미지가 아니라 작가 프로필·상품 설명에서 나올 말이다. 상위 태그의 절반 이상이 **지역과 촬영 종류**다.

**생성 코드는 repo 에 없다.** `generated_tags` 에 쓰는 코드가 어디에도 없고(읽기·삭제만 있다), git 삭제 이력·stash·형제 프로젝트·홈 디렉터리·Spotlight·Claude/Codex 대화 기록을 뒤져도 나오지 않았다. repo 밖에서 일회성으로 실행하고 커밋하지 않은 것으로 보인다. `scripts/export-tags.cjs` 는 `mood_tags` 집계 CSV 내보내기라 짝이 아니다.

> 같은 패턴이 세 번 반복됐다 — §4.4 의 명도/채도 지표 코드, `_migrations` 추적 중단(0047), 이 태그 배치. 모두 0047 즈음이고 모두 repo 밖 일회성 작업이다. **일회성이라도 `scripts/` 에 커밋할 것.**

#### 그래서 별도 공간을 썼다 (`0074`)

`generated_tags` 에 얹지 않고 새 컬럼을 만들었다. 출처가 다른 값을 섞으면 어느 것이 사람이 넣은 것이고 어느 것이 기계가 붙인 것인지 구분할 수 없게 된다. 6월 값은 **손대지 않았다** — 지역 정보(`서울`·`경기`·`천안`·`경복궁`)는 사진에서 뽑을 수 없는 값이라 버릴 이유가 없다.

| 컬럼 | 용도 |
|---|---|
| `auto_mood_tags text[]` | 무드 라벨(한글). GIN 인덱스 |
| `auto_mood_model text` | `<모델명>@<어휘버전>` — 0068 `embedding_model` 과 같은 규칙(§6) |
| `auto_mood_at timestamptz` | `null` = 배치 대상. 0047·0068 과 같은 큐 패턴 |

**점수 컬럼을 두지 않았다.** `photos.embedding`(0068)이 이미 저장돼 있어 어휘가 바뀌어도 **사진 재다운로드 없이** 태그를 다시 계산할 수 있다. 임베딩이 durable 산출물이고 태그는 파생물이다. 실제로 전체 임베딩을 PostgREST 로 받는 데 26MB · 4초면 된다.

#### 어휘 설계 (`mood-v1`, 45개)

**촬영 종류를 넣지 않았다.** 웨딩·커플·가족 같은 말은 어휘에 없다. 그것은 타겟 축이 담당한다 — PR #267 에서 `감성`·`빈티지`·`여행` 같은 범용 태그 하나만 걸쳐도 매칭이 성립해 개인 스냅 피드에 웨딩·커플 208장이 섞여 들어갔고, 결론이 **"촬영 종류는 태그가 아니라 타겟 멤버십으로 판단한다"** 였다. 기계가 어휘를 촘촘히 붙이면 이 문제를 증폭시킨다.

> **사진이 크게 늘면 촬영 종류를 다시 넣는 편이 나을 수 있다.** 규모가 커지면 태그가 세분화돼 과매칭이 줄기 때문이다. 현재 규모(1,763장)에서는 추천을 강제하는 쪽으로 작용해 뺐다. 재검토 시 이 판단부터 다시 볼 것.

갈래는 색조 9 · 빛 10 · 분위기 12 · 질감 10 · 공간 4 다. **프롬프트는 영어, 라벨은 한글** — SigLIP 은 영어 학습이 지배적이라 한글 프롬프트를 직접 넣으면 품질이 떨어진다.

#### 함정 두 가지

**1. 절대 확률로 임계값을 잡으면 아무 태그도 안 붙는다.**

SigLIP 은 CLIP 과 달리 sigmoid 손실로 학습돼 `sigmoid(logit_scale·cos + logit_bias)` 가 태그별 독립 확률이 된다(softmax 를 씌우면 안 된다). 그런데 이 값이 추상적 스타일 문구에 대해 극도로 보수적이다.

```
logit_scale = 113.73 · logit_bias = −15.94
어휘 45개 전부 최대 확률 < 0.5   (제일 높은 '실내 자연광' 이 0.436)
```

그래서 **카탈로그 대비 z-score 상위 N개**로 태그를 정한다. "이 사진은 남들보다 유난히 노을빛" 이라는 상대 판정이다.

**2. 순위 방식이라 "맞는 사진이 없어도 상위는 채워진다".**

z-score 는 순위만 주므로, 진짜 흑백 사진이 한 장도 없어도 `흑백` 상위 12장은 무조건 채워진다. **픽셀로 잴 수 있는 것을 텍스트 타워에 묻지 말 것.** `흑백` 은 프롬프트에서 빼고 chroma 로 측정하도록 바꿨다.

```
chroma 평균 분포(표본 300장)  0% 0.09(완전 그레이스케일) · 5% 4.18 · 50% 12.53
기준: chroma < 3.0 이고 표준편차 < 6.0   (스팟 컬러 제외)
결과: 공개 1,763장 중 42장(2.4%)에만 부여 — 조건을 만족하는 만큼만 붙는다
```

이 갈래(**측정 태그** vs **프롬프트 태그**)는 앞으로도 유효하다. `밤`·`강한 대비`·`채도 낮은` 처럼 픽셀로 재는 편이 나은 것이 더 있으면 같은 방식으로 옮긴다.

#### 생성 결과

```
공개 1,763장 · 반영 1,763장 · 대기 0 · 실패 0 · 소요 91초
모델 태그  siglip2-so400m-patch16-naflex@mood-v1
어휘 45종 전부 사용 · 사진당 정확히 5.0개 · 총 8,857건
최다 도시적인 338 · 실내 자연광 338 / 최소 흑백 42 · 플랫한 75
```

#### 소비처를 찾다 — v2 무드 카테고리 자동 배정 검토

`feed_photos_taste` 가 죽었으므로, 지금 살아 있는 축인 **v2 무드 카테고리**(`explore_categories.kind='mood'` 5개)에 사진을 자동 배정하는 방안을 검토했다. 운영자가 어드민에서 손으로 하는 일이다.

운영자가 만든 1,528행을 정답지로 삼아 5-fold 교차검증으로 측정했다. **이 과제에서 처음으로 눈이 아니라 숫자로 판정할 수 있는 지점이었다.**

| 무드 카테고리 | 멤버 | 무작위 기대 | 태그 기반 | 임베딩 기반 |

| 감성-시네마틱 | 235 | 7.0 | **27.6 (3.9배)** | 10.0 (1.4배) |
| 내추럴 | 371 | 18.8 | **60.8 (3.2배)** | 37.2 (2.0배) |

신호는 있다. 그리고 **45개 태그가 1,152차원 임베딩을 이겼다** — 무드 카테고리가 거친 축이라 압축된 표현이 잡음을 덜 타는 것으로 보인다.

lift 분석(대응표를 손으로 짜지 않고 데이터에서 뽑은 것)도 어휘가 의미를 잡고 있음을 보여준다.

**그런데도 자동 배정은 하지 않았다.** 세 가지 이유다.

1. **절대 정확도가 낮다.** 5.6배여도 상위 230장 중 37.6장만 맞는다. 그대로 반영하면 10장 중 8장 이상이 운영자 기준과 다르다. (정답지 커버리지가 13~22% 라 "틀린 것처럼 보이는" 상당수가 미배정일 뿐일 수도 있는데, **지금 데이터로는 이 둘을 가를 수 없다.**)
2. **시크-모던과 감성-시네마틱을 구분하지 못한다.** 둘 다 상위가 `어두운`·`밤`·`짙은 색감`·`드라마틱한` 으로 거의 같은 얼굴이다.
3. **무엇보다 증상이 없다.** ↓

#### 결정적 측정 — 취향 피드는 이미 꽉 찬다

무드 카테고리 커버리지가 13~22% 라 얇아 보였다. 그래서 **그것이 사용자 화면에 문제로 나타나는지** 재봤다.

목적 3개 × 무드 조합 36가지를 전부 시뮬레이션한 결과다.

```
모든 조합에서  head = 200 / 200 (cap 상한)
1~4페이지 전부 48/48 장이 취향 멤버로 채워짐 — 예외 0건
```

`fetchTasteHeadIds` 는 `목적∩무드` → `목적만` → `무드만` 순으로 이어붙이는데, **`목적만`+`무드만` 만으로도 이미 200장을 넘긴다.** 가장 빈약한 조합(웨딩 × 시크-모던, 교집합 12장)조차 508장이 후보라 cap 에 걸린다. 일반 시드 피드로 넘어가는 것은 5페이지째부터다.

**즉 멤버를 늘려도 이미 꽉 찬 200장을 다른 200장으로 바꿀 뿐이고, 그것이 더 나은 200장인지 판단할 방법이 없다.** 7단계와 같은 결론이다 — 처방할 증상이 없다.

#### 재개 조건

- 취향 피드 머리가 실제로 모자라기 시작할 때 (사진이 줄거나 목적/무드가 세분화되면)
- 어드민에 **추천 후보 UI** 를 붙일 때 — 자동 배정을 그대로 반영하는 대신 "이 사진들이 '필름-빈티지' 같습니다" 를 무작위 대비 2~5배 정확한 순서로 제시하고 사람이 승인하는 방식. 커버리지를 손으로 올리는 것보다 빠르고, 틀려도 사람이 거른다. 그렇게 쌓인 검수 결과가 다음 라운드의 정답지가 된다

`auto_mood_tags` 는 그대로 둔다. 읽는 코드가 없으므로 위험이 없고, 재개 시 바로 쓸 수 있다. 어휘를 바꾸려면 `moods.VERSION` 을 올리고 `mood_tags.py` 를 다시 돌리면 된다(사진 재다운로드 없음).

### 7.6 7단계 — 톤 가중치 검토 결과 (도입하지 않음)

§4.6 판정이 "무드가 잘 맞는다" 로 나와 7단계는 착수하지 않기로 했다. **다만 접기 전에 오프라인으로 시험은 해봤다.** 다음 사람이 같은 실험을 처음부터 반복하지 않도록 결과를 남긴다.

**한 일**: 톤 디스크립터를 구현하고, α 를 바꿔가며 top-10 이 어떻게 달라지는지 렌더해 눈으로 비교했다.

```
유사도 = α × (SigLIP 코사인) + (1−α) × (톤 코사인)     α=1.0 이 현재 동작
```

**DB·앱은 건드리지 않았다.** 표본 300장과 1단계 임베딩 캐시만 읽는 읽기 전용 하네스다.

#### 실측 (표본 300장 · 시드 12개 · top-10 · 같은 게시물 제외)

| α | 시드와 명도차 | 채도차 | 같은 작가% | 작가 수 | α=1.0 유지율 |
|---|---|---|---|---|---|
| **1.0 (현재)** | 0.145 | 0.071 | 24.2 | 3.58 | 100% |
| 0.9 | 0.128 | 0.070 | 21.7 | 3.83 | 83% |
| 0.8 | 0.102 | 0.066 | 22.5 | 4.00 | 65% |
| 0.7 | 0.085 | 0.061 | 21.7 | 4.17 | 49% |
| 0.5 | 0.071 | 0.053 | 21.7 | 4.50 | 33% |

기계적으로는 의도대로 동작한다 — α 를 낮출수록 시드와 톤이 가까워지고(0.145 → 0.071), 작가 다양성은 늘고, 같은 게시물 비중은 나빠지지 않는다.

**같은 작가% 가 α 와 무관하게 21~24% 로 고정인 점**은 기록해둘 만하다. "톤 = 작가 색깔이라 결국 한 작가 사진만 나올 것" 이라는 우려가 데이터상 나타나지 않았다. 7단계의 잠재적 실패 모드 하나는 배제된다.

#### 반드시 알아야 할 함정 — 두 축의 분산이 4.3배 다르다

|  | 평균 | 표준편차 |
|---|---|---|
| SigLIP 코사인 | +0.657 | **0.080** |
| 톤 코사인 | −0.001 | **0.348** |

SigLIP 유사도는 좁은 띠에 몰려 있고 톤은 넓게 퍼진다. **그대로 섞으면 α=0.9 인데도 top-10 의 절반이 갈린다** — 이름은 "톤 10%" 인데 실제로는 순위 변동의 3분의 1을 톤이 좌우한다. α 를 눈으로 골라야 하는데 눈금이 거짓말을 하는 셈이다.

표준편차로 나눠 맞춘 뒤 섞어야 α 가 제 뜻을 갖는다(톤에 ×0.231). **프로덕션에서도 상수 하나를 곱하는 것이라 비용이 없다.** 이 보정을 모르고 시작하면 반드시 한 번 헤맨다.

#### 도입하려면 (설계만, 미구현)

- **별도 컬럼 + RPC 재랭킹.** `0069` 가 이미 후보를 300장 뽑으므로 그것만 혼합 점수로 다시 정렬하면 된다. HNSW 인덱스를 건드리지 않는다
- **α 는 RPC 파라미터로.** 기본값 `1.0`(= 무동작)으로 배포하면 배포 자체가 안전하고, 값을 내리는 것만으로 켤 수 있다. 되돌리기도 `1.0` 복귀
- 임베딩에 이어붙이는 방식은 차원이 바뀌어 §9.3 3번(컬럼 타입 변경)에 걸리고 α 조정마다 전량 재백필이라 택하지 않았다

#### 재검토 조건

- §4.6 판정이 뒤집힐 때 — 사진이 늘면서 "피사체만 맞는다" 가 관찰되기 시작하면
- 추천 클릭 데이터가 쌓여 **눈대중이 아니라 측정으로** α 를 고를 수 있게 될 때. 지금 접는 가장 큰 이유가 "좋아졌는지 확인할 방법이 없다" 는 것이다

관련 코드:

- `scripts/embed/tone.py` — CIELAB 22차원 톤 디스크립터. 모델 불필요, 300장에 1초
- `scripts/embed/eval_tone.py` — α 비교 하네스. `--standalone` 은 이미지를 박아 공유용 단일 파일로 만든다

### 7.7 곁가지 발견 — 취향 테스트 '목적' 축 오배선 → **[docs/23](23-taste-purpose-mapping.md)**

§7.5 의 8단계 측정 중에 나온 **별개 건**이다. 시각 유사도와 무관해 문서를 나눴다. 여기서는 발견 사실만 남긴다.

**증상**: 취향 테스트에서 "커플 스냅" 을 고르면 홈 피드 후보 256장 중 **142장이 웨딩 앨범 사진**이다(정확도 35%). 웨딩·개인 목적은 86~98% 로 정상이다.

**원인**: 목적 축이 촬영 종류를 타겟 멤버십이 아니라 탐색 카테고리 슬러그로 판단하는데, 커플이 참조하는 `couple`·`friends` 가 실재하지 않아 `date`(데이트) 하나만 남는다. `resolveCategoryIdsBySlugs` 가 `.in()` 이라 **없는 슬러그를 조용히 버린다.**

**이 문서와 이어지는 점** — 이 건이 §7.5 의 결론을 바꾸지는 않는다. 취향 피드 머리는 어차피 200/200 으로 차므로(§7.5) 자동 무드 태그로 멤버를 늘려도 증상이 개선되지 않는다. **취향 피드 품질에 실제로 효과가 있는 것은 자동 태그가 아니라 이쪽이다.**

원인·실측·수정안·검증 방법은 전부 [docs/23](23-taste-purpose-mapping.md) 에 있다. 감사 스크립트는 `scripts/audit-taste-purposes.cjs`.

## 9. 운영 절차

### 9.1 사전 측정 재실행

§3 수치는 아래 한 줄로 재생성한다. 읽기 전용이며, 외부 패키지가 없어 venv 없이 시스템 python 으로 바로 돈다.

```bash
python3 scripts/embed/check_db.py
```

규모·저장량 추정·이미지 실측·비율 분포를 출력한다. `0068` 적용 후에는 **임베딩 대기 장수**가 함께 나오므로 백필 진행률 확인에도 쓴다.

pgvector 설치 여부만은 PostgREST 로 시스템 카탈로그를 읽을 수 없어 SQL Editor 에서 직접 확인한다(스크립트 마지막에 쿼리를 출력한다).

### 9.2 백필 재실행 / 신규 사진 처리

```bash
python scripts/embed/embed_photos.py                       # dry-run (기본값)
python scripts/embed/embed_photos.py --apply --limit 10    # 소량 검증
python scripts/embed/embed_photos.py --apply               # 전체
```

`embedded_at is null` 인 사진만 처리하므로 **중단 후 재실행해도 이미 끝난 사진을 다시 계산하지 않는다.**

**"전송 N장" 을 반영 수로 믿지 말 것.** PostgREST 는 매칭 0행인 PATCH 에도 204 를 돌려주므로, 배치가 도는 동안 삭제된 사진은 에러 없이 성공으로 세어진다. 실제 반영 여부는 스크립트가 마지막에 출력하는 **커버리지** 줄로 확인한다.

배치가 끝나도 대기가 남는 것은 정상이다. 도는 동안 새로 올라왔거나 비공개→공개로 전환된 사진이며, 같은 명령을 다시 실행하면 그것만 처리한다.

> 2026-08-06 실행 사례: 11분간 백필이 도는 사이 운영 측에서 사진 29장 삭제·36장 추가가 있었다. 삭제된 29장에 대한 PATCH 는 조용히 성공 처리됐고, 새로 공개된 32장이 대기로 남아 재실행으로 마무리했다.

**무드 태그도 같은 방식이다**(§7.5). 임베딩 백필과 별개 큐이므로 신규 사진이 생기면 둘 다 돌려야 한다 — 임베딩이 먼저다(무드 태그가 그것을 입력으로 쓴다).

```bash
scripts/embed/.venv/bin/python scripts/embed/mood_tags.py                     # dry-run
scripts/embed/.venv/bin/python scripts/embed/mood_tags.py --apply --limit 10  # 소량 검증
scripts/embed/.venv/bin/python scripts/embed/mood_tags.py --apply             # 대기분만
scripts/embed/.venv/bin/python scripts/embed/mood_tags.py --apply --all       # 전량 재계산
```

`auto_mood_at is null` 이거나 `auto_mood_model` 이 현재 어휘 버전과 다른 사진만 쓴다. 어휘를 바꿨으면 `moods.VERSION` 을 올리는 것만으로 전량이 자동으로 대상이 된다.

**사진을 내려받지 않는다** — 저장된 `photos.embedding` 을 쓴다(전량 26MB · 4초). 단 측정 태그(흑백)는 픽셀이 필요해 **대상 사진의 thumb 만** 받는다. `--no-measured` 로 끄면 그마저 없어진다.

> z 기준 때문에 매 실행마다 공개 사진 **전체**의 임베딩을 받는다. 일부만 받아 z 를 내면 그 배치의 기준이 기존 행과 어긋나 태그가 미묘하게 달라진다. **받는 것은 전체, 쓰는 것은 대상만.**

### 9.3 모델·해상도 교체

1. `embedding_model` 로 대상 행을 식별한다(값 형식은 §6).
2. 차원이 같으면 해당 행의 `embedded_at` 을 `null` 로 되돌려 큐에 재투입한다.
3. 차원이 다르면 컬럼 타입 변경이 필요하다 → 새 마이그레이션.

**교체 중 서비스는 정상 동작한다.** 배치가 도는 동안 일부는 구 설정, 일부는 신 설정 벡터인 상태가 되지만, 같은 사진의 `256` 벡터와 `1024` 벡터의 코사인 유사도가 **평균 0.955**(최소 0.872)로, "가장 비슷한 남의 사진"(평균 0.871)보다 가깝다. 설정이 바뀌어도 그 사진은 벡터 공간에서 거의 제자리에 있으므로 섞인 상태의 검색 결과가 무너지지 않는다. 원자적 교체를 설계할 필요가 없다.

`256 → 1024` 전환 실비용: 마이그레이션 불필요(차원 동일) · 앱 코드 변경 없음 · 재계산 약 4분.

### 9.4 스크립트 실행 환경

임베딩 배치는 Python 이다. 시스템 Python(3.9)에 직접 설치하지 말고 **venv 로 격리**한다. 단 `check_db.py` 는 표준 라이브러리만 쓰므로 venv 없이 돈다.

> 참고: 2026-08-05 기준 작업 머신에 `node` 가 없어 `0068`·`0069` 는 SQL Editor 로 적용했다. **2026-08-07 확인 시 `node` v26.6.0 설치됨** — 이후 마이그레이션은 `scripts/migrate.cjs` 를 쓸 수 있다. 단 **인자 없이 실행하면 안 된다.** 이유와 올바른 호출법은 §10.2.

## 10. 안전장치

프로덕션 DB(`main`)를 직접 변경하므로 아래를 지킨다.

### 10.1 원칙

**이 과제의 모든 DB 변경은 추가형이다.** 기존 컬럼을 수정하거나 삭제하는 작업이 하나도 없다. 따라서 전체 롤백이 아래 세 문장으로 끝난다.

```sql
-- 0068 (사용 중 — 되돌리면 사진 상세 추천이 태그 폴백으로 떨어진다)
drop function if exists public.similar_photos_by_embedding(uuid, integer);
drop index if exists public.idx_photos_embedding_hnsw;
drop index if exists public.idx_photos_embedding_pending;
alter table public.photos
  drop column if exists embedding,
  drop column if exists embedding_model,
  drop column if exists embedded_at;

-- 0074 (읽는 코드 없음 — 언제 지워도 아무 영향 없다)
drop index if exists public.idx_photos_auto_mood_tags;
drop index if exists public.idx_photos_auto_mood_pending;
alter table public.photos
  drop column if exists auto_mood_tags,
  drop column if exists auto_mood_model,
  drop column if exists auto_mood_at;
```

확장까지 되돌리려면 `drop extension vector;` (해당 타입을 쓰는 컬럼이 없을 때).

`0074` 는 **읽는 코드가 없으므로 롤백에 서비스 영향이 전혀 없다.** 반대로 `0068` 은 사용 중이라, 되돌리면 `similar_photos_by_embedding` 이 빈 배열을 주고 추천이 기존 태그 방식으로 떨어진다(§7.2 의 폴백). 화면이 비지는 않는다.

### 10.2 마이그레이션 적용 방법

**항상 파일명을 인자로 준다.**

```bash
node scripts/migrate.cjs 0074_photo_tone_descriptors    # 예시
```

`node` 가 없으면 Supabase 대시보드 **SQL Editor** 에 `.sql` 내용을 붙여 넣는다. 어느 쪽이든 파일은 `supabase/migrations/` 에 커밋해 재현 가능하게 남긴다. **대시보드에서 손으로 실행한 변경은 반드시 같은 내용의 마이그레이션 파일을 남길 것.**

#### 인자 없이 실행하지 말 것 (2026-08-07 확인 · 08-08 갱신)

`_migrations` 추적 테이블이 **`0047` 에서 멈춰 있다.** `0048` 이후로 **32개가 프로덕션에 적용됐지만 기록이 없다.** 한동안 팀 전체가 SQL Editor 로만 적용해온 결과다.

> `0048` 이후 기록된 것은 `0074_photo_auto_mood_tags.sql` 하나뿐이다. `migrate.cjs` 접속을 고친 뒤(§11) 정규 경로로 적용한 첫 파일이라 자동으로 기록됐다. **접속 문제가 해결됐으니 앞으로 정규 경로를 쓰면 이 격차는 더 벌어지지 않는다.**

인자 없이 실행하면 그 31개를 "미적용" 으로 보고 전부 다시 돌린다. 실제 위험도는 이렇다.

| 문장 유형 | 재실행 시 | 위험 |
|---|---|---|
| `create table/index if not exists`, `add column if not exists` | 통과하거나 `already exists` → 스크립트가 잡아서 적용 처리 | 없음 |
| 시드 `insert` (`0060`·`0061`·`0068_target`) | 전부 `on conflict do nothing` | 없음 (확인함) |
| **`create or replace function`** | **에러 없이 파일 내용으로 덮어씀** | **있음** |

마지막 줄이 문제다. 에러가 안 나므로 스크립트의 `already exists` 자가 치유가 작동하지 않고, **프로덕션에서 손으로 고쳐둔 함수가 있다면 조용히 되돌아간다.** 31개 파일이 전부 파일 == 프로덕션인지는 검증되지 않았다.

**해소 방법**: `_migrations` 에 31개 이름을 채워 추적을 사실과 맞춘다. 한 문장이면 되지만 "이것들은 적용됐다" 고 단언하는 일이라 **팀 합의 후 실행한다.** 그 전까지는 인자를 반드시 준다.

#### 필터는 부분 문자열 매칭이다

`migrate.cjs` 는 `f.includes(filter)` 로 파일을 고른다. 번호만 주면 **같은 번호의 다른 파일까지 걸린다.**

```bash
node scripts/migrate.cjs 0068     # ✗ 세 파일이 전부 실행된다
```

이 repo 는 번호가 겹쳐 있다 — `0068` 3개, `0069` 3개, `0074` 2개, 그 밖에 `0040`·`0041`·`0045`·`0055` 가 2개씩. 브랜치들이 동시에 같은 번호를 집었고 git 은 파일명이 달라 충돌로 보지 않는다.

> **`0074` 는 이 경고를 쓴 바로 다음 PR 에서 또 겹쳤다 (2026-08-08).** `0074_photo_auto_mood_tags.sql`(§7.5)과 `0074_photo_feed_hidden.sql`(PR #268)이 같은 날 들어왔다. 서로 다른 브랜치에서 동시에 작업하면 **번호 규칙만으로는 막을 수 없다.** 브랜치를 딸 때 `origin/main` 의 최신 번호를 확인하고, PR 을 올릴 때 한 번 더 보는 수밖에 없다.

이미 적용된 것들이라 번호를 되돌리는 것은 위험하고 실익도 없다. **다음 번호는 `0075` 부터 쓰고, 인자에는 번호가 아니라 파일명 앞부분을 충분히 길게 준다.**

### 10.3 백필 전 스냅샷

3단계는 이 과제에서 **유일하게 실제 데이터를 쓰는 단계**다. 직전에 스냅샷을 뜬다(1,610행이라 1초).

```sql
create table photos_backup_YYYYMMDD as select * from photos;
```

결과 확인 후 `drop table photos_backup_YYYYMMDD;`

### 10.4 배치 스크립트 규칙

`SUPABASE_SERVICE_ROLE_KEY` 는 **RLS 를 전부 우회**한다. 이 과제에서 가장 날카로운 부분이므로 아래를 지킨다.

- `where id = '...'` 없는 `update` 를 **작성하지 않는다**
- `--dry-run` 이 기본값. `--apply` 를 명시해야 DB 에 쓴다
- 건드리는 컬럼은 `embedding`, `embedding_model`, `embedded_at` **셋뿐**. 나머지는 읽기만
- 전체 실행 전 `--limit 10` 으로 먼저 검증

### 10.5 Storage 는 건드리지 않는다

Supabase 일일 백업에는 **Storage 객체(사진 원본)가 포함되지 않는다.** 다행히 이 과제는 Storage 를 **읽기만** 한다(`thumb_url` 다운로드). 쓰기·삭제가 없으므로 이 제약은 영향이 없다.

- **명령어 자체는 여기 적지 않는다.** 반복 실행할 것은 전부 `scripts/` 에 두고 문서는 그것을 가리킨다(§9). 문서에 복붙한 명령어는 스키마·URL 이 바뀌어도 조용히 낡기 때문이다.
