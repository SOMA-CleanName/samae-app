## 1.3 접근 경로와 권한 경계 — 이 서비스의 핵심 규칙

| 작업 | 경로 | 키 | 강제 수단 |
|---|---|---|---|
| 공개 조회 (탐색·피드·작가 프로필) | 서버 컴포넌트 | anon + RLS(public read) | RLS 정책 |
| 본인 데이터 (내 문의·프로필·채팅) | 서버/클라 컴포넌트 | anon + RLS | RLS 정책 |
| 리드 연락처 노출 | 서버 전용 모듈 (`lib/inquiries.ts`) | service_role | **select 목록에서 연락처 컬럼 제외** — 잠긴 리드는 네트워크 응답에도 값이 실리지 않음 |
| 상태 전이 (문의 수락·입금 확인·만료·작가 승인) | 서버 액션 / Route Handler / RPC | service_role | 서버에서만, 감사 컬럼 동반 |
| 근접검색·피드 쿼리 | Postgres RPC (`security definer`) | — | 함수 안에서 노출 규칙 재확인 |
| 크론 | `/api/cron/*` | service_role | `Authorization: Bearer $CRON_SECRET` 검증 |
| 익명 추적 수집 | `/api/track` | service_role | **same-origin 검증**(Origin→Referer), 어드민·스튜디오 경로 제외 |

> 원칙: **돈·상태·연락처를 움직이는 일은 클라이언트가 직접 못 한다.** 게이트는 UI가 아니라 쿼리 레벨에 있다.

## 1.4 주력 비즈니스 흐름 — 리드 언락

현재 매출 동선은 예약·에스크로가 아니라 **리드 언락**이다. (예약 상태머신·PG 코드는 남아 있으나 주력 플로우가 아님)

```
[고객]  탐색/피드 → 사진 선택 → 문의 위저드(목적·일정·지역·인원·참고사진)
          │  utm·Meta 쿠키 스냅샷 동반 저장 (0055/0057)
          ▼
      inquiries INSERT  ──▶ Discord 문의 채널 알림(운영진)  ──▶ Meta CAPI Lead 전송
          │
          ▼
[작가]  받은 문의 카드 — 브리프·신청 사진은 보이고 **연락처만 잠김**
          │  해제 신청 → 플랫폼 계좌(platform_account) 무통장 입금 → '입금완료' 신고
          ▼
[운영]  어드민에서 입금 확인 → confirmed=true → 연락처 공개
          │
          ▼
      7일 무반응 리드는 크론이 expired 전이 (멱등)
```

관련: `lib/inquiries.ts`, `lib/ops-alert.ts`, `lib/meta-capi.ts`, `lib/inquiry-expiry.ts`, 마이그레이션 0064·0072·0076.

# Part 2. AI 활용 전략

## 2.1 AI 자산 3층 — 현재 가동 중인 것

```
┌─ 층 1 · 언어/비전 모델 (Claude) ──────────── 온디맨드, 사용자 요청 시 ─────────┐
│  페르소나 이벤트  /event/persona                                            │
│   IG username → Apify 수집 → Stage1 심리 프로파일 → Stage2 촬영 페르소나        │
│   → 목적·무드 매핑 → taste v2 쿠키 → 홈 피드가 즉시 개인화됨                     │
└──────────────────────────────────────────────────────────────────────────┘
┌─ 층 2 · 이미지 임베딩 (SigLIP2) ──────────── 오프라인 배치, 조회 시 추론 0 ─────┐
│  공개 사진 전량 → 1152차원 벡터 → photos.embedding(halfvec) + HNSW           │
│   → similar_photos_by_embedding RPC                                        │
│   → 사진 상세 "이런 사진은 어때요?" · 홈 클릭 기반 개인화                        │
└──────────────────────────────────────────────────────────────────────────┘
┌─ 층 3 · 파생물 (auto_mood_tags) ─────────── 임베딩 재사용, 현재 보류 ─────────┐
│  SigLIP 텍스트 타워 × 저장된 임베딩 → z-score 상대 태그 → photos.auto_mood_tags│
│   생성은 완료, **소비처 미연결** — 처방할 증상이 실측되지 않아 의도적 보류          │
└──────────────────────────────────────────────────────────────────────────┘
```

### 층 1 — LLM 파이프라인 상세

| 단계 | 입력 | 처리 | 출력 |
|---|---|---|---|
| 수집 | IG username | Apify actor 동기 실행(최근 20건, 120s 타임아웃) | 프로필·게시물·지표 |
| Stage1 | 지표 + 캡션 + **이미지 최대 3장** | 계산심리학 근거를 프롬프트에 명시(Back 2010 / Kosinski) · Big5 점수는 신호 강도에 따라 확신 차등 | `Persona` (Zod 스키마) |
| Stage2 | Stage1 결과 + 정량 지표 + **런타임 무드 카탈로그** | 목적(personal/couple/wedding) 판별 + 무드 1~3개 매핑 | `ShootPersona` |
| 후처리 | Stage2 출력 | **서버측 화이트리스트 필터** — 카탈로그에 없는 무드 id는 제거, 근거문도 함께 정리 | taste v2 쿠키 |

구현 특징 (`src/lib/persona/`):
- `client.messages.parse()` + `zodOutputFormat(Schema)` — 구조화 출력을 SDK 레벨에서 강제, 파싱 실패 시 1회 재시도
- `thinking: { type: "disabled" }`, `max_tokens: 2000` — 이벤트 UX상 지연을 억제
- 무드 카탈로그를 하드코딩하지 않고 **런타임에 DB에서 주입** → 운영이 카테고리를 바꿔도 코드 수정 불필요
- 비공개/게시물 없음 계정은 `PersonaScrapeError` → 사진 직접 업로드 폴백 경로로 유도

### 층 2 — 임베딩 파이프라인 상세

| 결정 | 값 | 근거 |
|---|---|---|
| 모델 | `google/siglip2-so400m-patch16-naflex` | 오픈 웨이트, 호출 과금 없음 |
| 비율 처리 | naflex(원본 종횡비 보존) | 공개 사진의 80% 이상이 세로 — 정사각 리사이즈는 구도를 뭉갬 |
| 해상도 예산 | `max_num_patches=256` | thumb(500×750)로 충분, 1024와 육안 품질 차 없음 |
| 저장 | `halfvec(1152)` | 정밀도 손실 없이 용량 절반 |
| 인덱스 | HNSW cosine, `visibility='published'` 부분 인덱스 | 빌드 시간·크기 절감. 작가 승인 여부는 조인에서 재확인 |
| 폴백 | 임베딩 없는 신규 사진 → 태그 기반 추천 | 배치 지연이 화면 결손이 되지 않음 |

## 2.2 설계 원칙 5가지 — 그대로 유지할 것

1. **조회 시점 추론 0.** 사용자가 화면을 여는 경로에는 어떤 모델도 돌지 않는다. 추론은 오프라인 배치(층 2·3)이거나 사용자가 명시적으로 시작한 이벤트(층 1)일 때만 발생한다. → 응답 지연·GPU 상시 비용이 구조적으로 0.
2. **LLM 출력은 신뢰하지 않고 검증한다.** 스키마는 Zod로, 값은 서버측 화이트리스트로 이중 검증. 모델이 없는 카테고리를 지어내도 화면에 도달하지 못한다.
3. **durable 산출물과 파생물을 분리한다.** 임베딩은 durable(재계산 비쌈), 태그는 파생물(어휘만 바뀌면 재계산 저렴). 그래서 어휘를 바꿔도 사진을 다시 내려받지 않는다.
4. **실측되지 않은 증상은 처방하지 않는다.** docs/22 의 6~8단계를 만들어놓고 연결하지 않은 것은 미완성이 아니라 판단이다. 지표 없이 붙인 AI 기능은 되돌리기 어려운 부채가 된다.
5. **배치 스크립트는 사고를 구조적으로 못 내게 만든다.** `--dry-run` 기본, `--apply` 명시 필요, update는 항상 `id=eq.<uuid>` 단건, 건드리는 컬럼은 3개로 고정. service_role이 RLS를 우회하는 위험을 이 규칙들이 감싼다.

## 2.3 비용 구조

| 항목 | 과금 | 특징 |
|---|---|---|
| 이미지 임베딩·자동 태그 | **0원** | 오픈 웨이트 로컬 실행. 전량(약 1,800장) 백필이 수 분 |
| 벡터 검색 | Supabase 포함 | 조회당 추가 과금 없음 |
| 페르소나 이벤트 | Anthropic 토큰 + Apify 호출 | **유일한 가변비.** 1회 = Stage1(이미지 3장 포함) + Stage2 |
| 참고 단가 | Opus 5 $5/$25, Sonnet 5 $3/$15, Haiku 4.5 $1/$5 (per MTok in/out) | 실제 1회 비용은 `count_tokens`로 실측 후 확정할 것 |

즉 **AI 비용은 사용자 수가 아니라 이벤트 참여 수에 비례**한다. 피드·추천은 사용자가 늘어도 AI 비용이 증가하지 않는 구조다.

## 2.4 로드맵

### 단기 (0~1개월) — 이미 아는 결함부터

| # | 과제 | 근거 |
|---|---|---|
| S1 | **모델 기본값 갱신** — 현재 `ANTHROPIC_MODEL` 기본값이 `claude-opus-4-8`. 최신 Opus 5(`claude-opus-5`)로 이관. 단, Opus 5는 **thinking이 기본 on**이고 `disabled`는 effort ≤ high 에서만 허용되므로 현재의 `thinking:{type:"disabled"}` 조합을 함께 점검 | 품질·비용 동시 개선 |
| S2 | **Stage별 모델 분리 스윕** — Stage1(심리 추론, 이미지 포함)은 상위 모델, Stage2(카탈로그 안에서 고르는 매핑 작업)는 Sonnet 5 / Haiku 4.5 후보. A/B로 품질 손실 없는 지점 탐색 | 가변비의 대부분이 Stage 2회 호출 |
| S3 | **취향 '목적' 축 오배선 수정** (docs/23) — 커플 판정 사용자에게 웨딩 사진 55%. 탐색 카테고리 슬러그가 아니라 타겟 멤버십을 보도록 재배선 + 슬러그 드리프트 경고 | AI 결과물의 품질이 아니라 **소비 경로**가 망가진 사례 |
| S4 | **임베딩 백필 자동화** — 신규 업로드 사진이 배치를 수동 실행할 때까지 추천 후보에서 빠진다. 업로드 훅 또는 크론으로 `embedded_at is null` 스윕 | 현재 유일한 운영 수동 개입 |

### 중기 (1~3개월) — 기존 자산 재활용

| # | 과제 | 방식 |
|---|---|---|
| M1 | **검색 벡터화** | SigLIP **텍스트 타워**를 이미 쓰고 있음(층 3). 같은 임베딩 공간에 검색어를 태워 텍스트→이미지 근접검색. 신규 모델·비용 0 |
| M2 | **자동 무드 태그 소비처 연결** | 원칙 4에 따라 먼저 측정 — "태그 미부착 사진의 노출 결손"을 수치화한 뒤에만 연결 |
| M3 | **문의 브리프 정규화** | 자유서술 메모 → 구조화(예산대·인원·분위기)해 작가 카드 가독성과 언락 전환 개선. 문의 접수 시 1회 호출이라 비용 예측 가능 |
| M4 | **작가↔리드 적합도 스코어** | 작가 포트폴리오 임베딩 평균 vs 고객이 신청한 사진 임베딩 코사인 → 운영진 배분 보조. **추론 0, 벡터 연산만** |

### 장기 (3개월+) — 데이터가 쌓인 뒤에만

| # | 과제 | 전제 조건 |
|---|---|---|
| L1 | 클릭·언락 로그 기반 학습형 랭킹 | 현재 개인화는 세션 한정(sessionStorage 8장). 계정 단위 장기 취향 프로필은 의도적으로 미적용 중 — 로그량 확보가 선결 |
| L2 | 리드 가격 최적화 | 언락 전환율·작가 유형별 데이터 축적 후 |
| L3 | 자동 큐레이션 제안 | 편집형 큐레이션의 운영 부하가 실제로 병목이 된 뒤에 |

## 2.5 리스크와 가드레일

| 리스크 | 현재 방어 | 보강 필요 |
|---|---|---|
| LLM 환각(없는 카테고리·과장된 심리 단정) | 화이트리스트 필터 + 프롬프트에 확신 차등 규칙 명시 + 부정 프레이밍 금지 | 결과 샘플 정기 리뷰 |
| 외부 의존 실패 (Apify 비공개/차단) | 명시적 에러 타입 → 업로드 폴백 경로 | 타임아웃·재시도 정책 문서화 |
| 개인정보 | Mixpanel PII 미전송, 연락처는 쿼리 레벨 게이트 | 페르소나 분석 원본 데이터 보존 범위 정의 |
| 설정 드리프트 (docs/23 사례) | — | 코드가 참조하는 슬러그/카테고리 존재 여부를 CI 또는 어드민에서 경고 |
| 배치 사고 (service_role) | dry-run 기본·단건 update·3컬럼 한정 | `_migrations` 추적 격차(docs/22 §12.2) 해소 |
| 모델 교체 | `embedding_model` / `auto_mood_model` 에 `<모델>@<설정>` 기록 → 점진 재계산 가능 | 유지 |

## 부록 · 한 문장 요약

> samae 의 AI는 **"조회 경로에서는 절대 추론하지 않는다"** 는 하나의 규칙 위에 서 있다. 무거운 계산은 오프라인 배치로 밀어 벡터로 저장하고(비용 0·지연 0), 언어 모델은 사용자가 명시적으로 시작한 이벤트에서만 돌리며, 그 출력은 반드시 서버가 검증한 뒤에야 화면에 도달한다. 그래서 사용자가 늘어도 AI 비용은 늘지 않고, 모델이 틀려도 화면은 깨지지 않는다.
