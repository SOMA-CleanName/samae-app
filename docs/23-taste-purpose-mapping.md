## 1. 증상

**"커플 스냅" 으로 판정된 사용자에게 웨딩 사진이 뜬다.** 후보 256장 중 142장(55%)이 웨딩 앨범 사진이다.

- **취향 테스트** → 홈 피드가 그 256장으로 채워진다
- **페르소나 이벤트** → 결과 화면의 "어울리는 사진" 9장이 그 안에서 뽑힌다 (더 직접적이다)

화면이 비거나 에러가 나지 않는다. 피드는 정상적으로 꽉 차므로 **겉으로는 아무 문제가 없어 보인다.** 다만 내용이 취향과 어긋난다.

**웨딩·개인 목적은 정상이다** (86% · 98%). 세 목적 중 하나만의 문제다. 영향받는 동선 전체는 §6.

---

## 2. 먼저 — 카테고리 탭은 멀쩡하다

"커플" 이 두 군데 있어 혼동하기 쉽다. **사용자가 카테고리에서 커플을 눌렀을 때 웨딩이 뜨는 문제는 없다.**

| 경로 | 무엇 | 사진 출처 | 상태 |
|---|---|---|---|
| `/c/couple` "커플·우정" | **타겟** 카테고리 | `resolveTargetPhotoIds` — 앨범 상속 | ✅ 정상 (170장, 전부 커플 앨범) |
| `/explore/date` "데이트" | **탐색** 카테고리 | `explore_category_photos` 수동 배정 | 256장 중 142장이 웨딩 앨범 |

`/c/<slug>` 는 PR #267 이 이미 타겟 멤버십으로 재배선했다. 이번 건은 **목적 축이 내부적으로 `/explore/date` 를 커플의 대역으로 쓰는 것**이고, 증상은 그 목적 축을 쓰는 동선(§6)에서만 나타난다.

---

## 3. 원인 — 카테고리 체계가 둘인데 잘못된 쪽을 본다

| 체계 | 테이블 | 내용 | 멤버십 결정 방식 |
|---|---|---|---|
| **타겟** (촬영 종류) | `categories` (4행) | wedding · couple · snap · etc | **앨범 상속** ∪ 수동추가 − 제외 |
| **탐색** (장면·무드) | `explore_categories` (26행) | `kind='mood'` 5 + `other` 21 | `explore_category_photos` 수동 배정 |

`taste-purposes.ts` 의 목적 3개(웨딩·커플·개인)는 **타겟 축과 같은 개념**이다. 그런데 구현은 `resolveCategoryIdsBySlugs()` 로 **탐색 카테고리** 슬러그를 찾는다.

```
사용자: "커플 스냅" 선택
   ↓
taste-purposes.ts   categorySlugs = ["couple", "date", "friends"]
   ↓                 couple · friends 는 explore_categories 에 없음 → 조용히 버려짐
   ↓                 date 하나만 남음
/explore/date 의 256장  →  그중 142장이 웨딩 앨범 사진
   ↓
fetchTasteHeadIds() → 홈 피드 상위 200장을 이것으로 채움
```

`wedding` 과 `couple` 은 **`categories`(타겟) 테이블에는 존재한다.** 두 체계의 슬러그를 혼동한 흔적으로 보인다.

## 4. 실측 (2026-08-08 · 공개 사진 1,763장)

| 목적 | 해석된 슬러그 | 존재하지 않는 슬러그 | 후보 | **후보 중 의도한 촬영 종류** | 그 종류를 담는 비율 |
|---|---|---|---|---|---|
| 개인 스냅 | profile-image · school-uniform | `profile` `graduation` `hanbok` | 576장 | **98%** | 45% |
| 웨딩 스냅 | studio-wedding · outdoor-wedding · casual-wedding · dress | `wedding` `wedding-ceremony` `self-wedding` | 302장 | **86%** | 75% |
| **커플 스냅** | **`date` 하나뿐** | `couple` `friends` | 256장 | **35%** | 53% |

**슬러그가 몇 개 없는지는 문제의 크기가 아니다.** 세 목적 모두 절반 가까이 빠졌지만, 웨딩·개인은 남은 슬러그가 제 역할을 해 86~98% 로 멀쩡하다. 유해한 것은 커플의 `couple`·`friends` 뿐이다.

커플 후보 256장의 실제 촬영 종류 분포:

```
couple  90장 (35%)   ← 의도한 것
wedding 142장 (55%)  ← 문제
snap     24장 (9%)
```

### 4.1 곁가지 — 비공개 카테고리를 쓰고 있다

개인 스냅이 참조하는 `school-uniform`(교복)은 **`published = false`** 다. `resolveCategoryIdsBySlugs` 는 공개 여부를 보지 않기 때문에 그대로 통과한다.

같은 파일의 `listMoodDeckForPurpose`·`listPublishedMoods` 는 `.eq("published", true)` 로 거른다. **동작이 일관되지 않는다.** 사진 자체는 공개된 것들이라 당장 사고는 아니지만, 운영자가 카테고리를 비공개로 내려도 취향 피드에는 계속 반영된다는 뜻이다.

## 5. 왜 아무도 몰랐나

`resolveCategoryIdsBySlugs` 가 이렇게 생겼다.

```ts
// src/lib/explore-db.ts
const { data } = await admin
  .from("explore_categories")
  .select("id")
  .in("slug", clean);   // ← 없는 슬러그는 그냥 안 맞히고 끝
```

**`in()` 은 없는 값에 대해 에러도 경고도 로그도 남기지 않는다.** 8개가 소리 없이 사라지고 남은 것으로 피드가 돈다.

게다가 **화면이 비지 않는다.** `fetchTasteHeadIds` 는 `목적∩무드` → `목적만` → `무드만` 순으로 이어붙이는데, 목적 후보가 줄어도 무드 쪽에서 채워져 상위 200장(cap)이 항상 찬다. 목적 3개 × 무드 조합 36가지를 전부 시뮬레이션해도 예외가 없었다.

즉 **"엉뚱한 200장이 채워질 뿐" 이라 발견이 늦는 종류의 결함**이다.

## 6. 영향 범위 — 취향 테스트만이 아니다

`resolveCategoryIdsBySlugs` 호출부는 **네 곳**이고, 전부 같은 목적 슬러그를 해석한다. 즉 **세 개의 사용자·운영 동선이 같은 결함을 공유한다.**

| 호출부 | 무엇에 쓰나 | 영향 |
|---|---|---|
| `explore/quiz/actions.ts:29` | **취향 테스트** — 퀴즈 결과를 `samae_taste2` 쿠키로 | ❌ 커플 선택 시 홈 피드 오염 |
| `event/persona/actions.ts:25` | **페르소나 이벤트** — 인스타 분석 결과로 쿠키 세팅 + "어울리는 사진" 9장 | ❌ 같은 문제. `fetchTasteCurated(purposeIds, …)` 로 추천 사진까지 틀어진다 |
| `persona/map-to-taste.ts:19` | 페르소나 → 쿠키 직렬화 (위와 같은 경로) | ❌ 동일 |
| `admin/explore/actions.ts:225` | **어드민** — (무드 × 목적) 대표 사진 후보 고르기 | 🟡 운영자가 **커플 목적의 대표 사진 후보로 웨딩 사진을 보게 된다** |

페르소나 이벤트가 특히 눈에 띈다. 취향 테스트와 달리 **결과 화면에서 "어울리는 사진" 9장을 바로 보여주므로**, 커플로 판정된 사용자에게 웨딩 사진이 즉시 노출된다. 취향 테스트는 홈 피드로 넘어간 뒤라 덜 직접적이다.

어드민 쪽은 사용자에게 안 보이지만, **운영자가 잘못된 후보 중에서 대표 사진을 고르면 그 결과가 `cover_by_purpose` 에 저장돼 취향 테스트 무드 덱에 노출된다.** 오염이 데이터로 굳는 경로다.

### 멀쩡한 것

| | 상태 |
|---|---|
| `/c/couple` 등 카테고리 탭 | ✅ 정상 (타겟 멤버십 — PR #267) |
| `/explore/date` 등 탐색 카테고리 페이지 | ✅ 정상 (의도대로 큐레이션 노출) |
| 취향 테스트·페르소나의 **무드** 축 (5개) | ✅ 정상 — 슬러그가 아니라 카테고리 ID 를 직접 쓴다 |
| **목적** 축 — 웨딩·개인 | 🟡 슬러그 일부 누락이나 결과는 86~98% |
| **목적** 축 — **커플** | ❌ **35%. 위 세 동선 모두 영향** |

**고칠 지점은 한 곳이다.** 네 호출부가 전부 `resolveCategoryIdsBySlugs` + `taste-purposes.ts` 를 거치므로, 그 한 쌍만 바로잡으면 셋 다 동시에 낫는다.

## 7. `/explore/date` 자체는 버그가 아닐 수 있다

"데이트" 는 운영자가 직접 고른 큐레이션이다. **장면·분위기로 묶은 모음이므로, 웨딩 앨범 사진이라도 데이트처럼 보이는 컷이면 거기 있는 것이 의도일 수 있다.**

이 문서는 그 컬렉션을 고치라는 것이 아니다. 잘못된 것은 그 장면 컬렉션을 **"커플 스냅이라는 촬영 종류" 의 대역으로 쓴 것**이다.

## 8. 고치는 방향

### A. 슬러그만 맞추기 (작음)

`taste-purposes.ts` 의 배열만 수정한다. 커플에 실재하는 슬러그를 넣거나 필요한 탐색 카테고리를 새로 만든다.

- 장점: 변경 범위가 파일 하나
- 단점: **같은 실수가 재발할 구조가 그대로다.** 누군가 또 없는 슬러그를 적으면 또 조용히 버려진다
- 현재 쓸 수 있는 비공개 카테고리: `studio` `striking-pose` `school-uniform` `vintage-look` `greenery` `city` `daily-life` (공개 전환 필요)

### B. 타겟 축으로 옮기기 (권장)

목적 = 촬영 종류이므로 `resolveTargetPhotoIds()` 를 쓴다.

- `categories` 4개와 목적 3개가 거의 1:1 대응한다 (wedding / couple / snap)
- **앨범 상속이라 신규 사진이 자동 반영된다.** 현재 앨범 155개 중 149개에 타겟이 지정돼 있다 (snap 102 · wedding 27 · couple 20, 미지정 6)
- PR #267 이 `/c/<slug>` 에 적용한 원칙을 취향 테스트에도 적용하는 것뿐이다
- 단점: `fetchTasteHeadIds` 가 목적·무드 양쪽을 `explore_category_photos` 한 곳에서 읽는 구조라, 목적만 다른 소스로 바꾸려면 그 함수를 손봐야 한다

### 어느 쪽이든 함께 할 것

**없는 슬러그가 조용히 버려지지 않게 한다.** `resolveCategoryIdsBySlugs` 에서 요청 수와 결과 수가 다르면 경고를 남기거나, 개발 환경에서 예외를 던진다.

`published` 처리도 함께 정한다 (§4.1) — 거를 것인지, 목적 축은 예외로 둘 것인지.

### 우선순위

개인·웨딩이 86~98% 로 멀쩡하므로 전면 개편이 급하지는 않다. **커플 하나만 바로잡아도 사용자가 체감하는 증상은 사라진다.** A 로 급히 막고 B 로 정리하는 순서도 가능하다.

## 9. 재현·검증

```bash
node scripts/audit-taste-purposes.cjs
```

읽기 전용이다. 목적별로 슬러그 해석 결과, 타겟 대비 정확도, 없는 슬러그·비공개 카테고리를 출력한다. 슬러그 목록은 `taste-purposes.ts` 에서 직접 읽으므로 **원본을 고치면 이 스크립트 결과도 따라 바뀐다.**

수정 후 **커플 정확도가 60% 이상**으로 올라가는지, 경고가 사라지는지로 확인한다.

2026-08-08 기준 출력:

```
■ 커플 스냅 (key=couple → 타겟 'couple')  ⚠️
   후보 256장 중 실제 couple = 90장  (35%)
   ❌ 존재하지 않는 슬러그 2개: couple, friends
   ❌ 정확도 60% 미만 — 나머지의 실제 타겟: wedding 142 · snap 24

발견된 문제 5건
```

## 11. 이 문서의 수명 — 고치면 지운다

**이 문서는 버그 하나를 팀에 전달하려고 만든 임시 문서다.** 22 처럼 설계 결정을 남기는 문서가 아니므로, 역할이 끝나면 `docs/` 에 남겨두지 않는다. 낡은 이슈 문서가 쌓이면 다음 사람이 "이게 아직 유효한 문제인가" 를 매번 확인해야 한다.

**삭제 조건 (전부 충족될 때)**

1. 수정이 `main` 에 머지됐다
2. `node scripts/audit-taste-purposes.cjs` 가 **커플 정확도 60% 이상**을 내고, "존재하지 않는 슬러그"·"비공개 카테고리" 경고가 사라졌다
3. 아래 두 가지가 각각 제자리에 남았다

**지우기 전에 옮길 것**

| 내용 | 옮길 곳 |
|---|---|
