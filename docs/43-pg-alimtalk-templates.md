> 거기가 운영이 읽는 곳이다. 넣어도 `PAYMENT_MODE=pg` 가 아니면 아무 일도 일어나지 않는다.

> 🟡 **아직 안 켰다.** 여기 적힌 문안을 솔라피 콘솔에 **새 템플릿으로 등록**해 두는 것이

> 찾는다(`ALIMTALK_TPL_<KIND>_PG`). 전환 전체 계획은 `docs/42-pg-switch-plan.md`.

## 왜 지금 하나

전환일에 밀리는 건 코드가 아니라 **남이 심사하는 것**이다. 약관 개정은 재동의,
알림톡은 템플릿 재심사 — 둘 다 우리가 당길 수 없다. 코드는 며칠이면 되는데 심사는 아니다.

**카카오는 템플릿을 독립적으로 승인한다.** 기존 승인 템플릿을 건드리지 않고 새 코드로
하나 더 등록할 수 있고, 보내지 않는 승인 템플릿이 있는 건 비용이 0이다. 그래서
"PG 문안" 을 지금 등록해 두면 전환일에는 **env 에 ID 를 넣는 일만** 남는다.

⚠️ **기존 템플릿을 수정하지 말 것.** 수정은 재심사고, 심사 중에는 카카오 본문(구)과
   문자 대체 본문(신)이 어긋난다(docs/34 §하단). 새로 만들어 나란히 둔다.

## 승인된 뒤

`.env`(프로덕션 포함)에 위의 env 키 셋을 넣는다. **넣어도 아무 일이 일어나지 않는다** —
`PAYMENT_MODE` 가 `pg` 가 아니면 코드가 이 키를 쳐다보지도 않는다.

```
ALIMTALK_TPL_BOOKING_ACCEPTED_PG=...
ALIMTALK_TPL_DEPOSIT_CONFIRMED_PG=...
ALIMTALK_TPL_BOOKING_CONFIRMED_PG=...
```

## 코드가 이미 보장하는 것

- **PG 문안이 있는 kind 만** `_PG` 키를 찾는다. 나머지 6종은 지금 ID 를 그대로 쓴다
  (없는 키를 기다리다 전부 문자로 떨어지는 사고 방지)
- PG 로 켰는데 `_PG` 템플릿이 아직 심사 중이면 **무통장 템플릿으로 떨어뜨리지 않는다.**
  차라리 문자로 나간다 — 카드로 결제한 고객이 "입금이 확인되어" 를 받는 것보다 낫다.
  문자 본문은 `notifyBody()` 가 결제 방식에 맞는 걸 고른다
- PG 문안이 원문과 **같은 변수**를 쓰는지 테스트가 막는다. 어긋나면 발송 시점에
  던져서 알림이 통째로 안 나간다
- PG 문안에 "입금"·"계좌" 가 남아 있으면 테스트가 실패한다

## 🔴 반려 — 카카오는 **결제 유도**를 막는다 (2026-09-21)

`예약 수락 - PG` 가 반려됐다. 사유 전문의 요지:

> 알림톡에서는 금융사고 예방 목적으로 **결제/송금/납부 유도 메시지를 허용하지 않는다.**
> 예외는 ① 금융위에 선불전자지급수단발행업·전자지급결제대행업(PG)·결제대금예치업(ESCROW)
> 중 **2개 이상 등록**된 업체 ② 카드사 연동 5개 이상인 휴대폰 제조사 결제대행 업체.

⚠️ **사매는 예외에 해당하지 않는다.** 통신판매중개자이고, PG 는 KG이니시스를 *쓰는* 것이지
   우리가 금융위에 등록한 것이 아니다. **결제 페이지를 캡처해 내도 통과하지 못한다.**
   그 길은 닫혀 있다고 보고 문안으로 푼다.

### 어디까지 되는가 — 승인·반려를 나란히 놓으면 선이 보인다

| | 문장 | 결과 |
|---|---|---|
| 완료 통보(과거) | "결제가 **완료되어** 예약이 확정됐어요" | ✅ 승인 |
| 조건 안내(미래) | "결제가 **완료되면** 예약이 확정돼요" | ❌ 반려 |

**미래형이 유도로 읽힌다.** 이미 끝난 일을 알리는 것은 되고, 앞으로 할 일을 말하면 안 된다.

### 고친 문안 — 결제를 아예 빼고 수락 사실만

```
[사매] 제안하신 예약을 #{상대명}님이 수락했어요.
· 촬영일: #{촬영일}
다음 단계는 예약 페이지에서 확인해 주세요.
#{링크}
```

다음에 무엇을 할지는 **지면에서** 안내한다. 알림톡은 "수락됐다" 만 말한다.

> 📌 테스트로 박았다 — PG 문안에 `결제 ~ 완료되면/하시면/해 주세요` 류가 있으면 실패한다.
> 같은 사유로 또 반려되는 일을 코드가 막는다.

### 이게 PG 전환 전체에 주는 뜻

**결제를 *요청*하는 알림톡은 앞으로도 못 보낸다.** 다행히 우리 9종은 전부 *완료 통보*라
영향이 없다. 다만 앞으로 "결제해 주세요" 류 리마인더를 만들고 싶어지면 알림톡이 아니라
**앱 안 알림이나 브랜드메시지**로 가야 한다(카카오 안내도 그렇게 권한다).

## `booking_accepted` 도 등록한다 (2026-09-19 결정)

이건 PG 에서 **안 쓰게 될 수도 있다.** 수락과 결제가 한 동작으로 합쳐지면 "수락했어요" 와
"결제됐어요" 사이에 알릴 틈이 없다. 결제창을 붙이며(docs/42 §3-3) 판가름 난다.

그래도 **등록한다.** 비대칭이 명백해서다 — 안 쓰면 승인된 템플릿 하나가 노는 것뿐이고
(비용 0), 필요해졌는데 없으면 그때 또 심사를 기다린다. 심사는 우리가 못 당기는 유일한
항목이라 여기서 아끼면 안 된다.

> 📌 셋 다 등록 대상이다. 결제창을 붙일 때 `booking_accepted` 가 실제로 나가는지만
> 확인하고, 안 나가면 그냥 두면 된다 — 지우려고 재심사를 걸 이유는 없다.
