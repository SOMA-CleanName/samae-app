# 43. PG 알림톡 템플릿 — 지금 심사 걸어 두기 (2026-09-19, 미시행)

> 🟡 **아직 안 켰다.** 여기 적힌 문안을 솔라피 콘솔에 **새 템플릿으로 등록**해 두는 것이
> 이 문서의 전부다. 등록해도 나가지 않는다 — 코드가 `PAYMENT_MODE=pg` 일 때만 이 ID 를
> 찾는다(`ALIMTALK_TPL_<KIND>_PG`). 전환 전체 계획은 `docs/42-pg-switch-plan.md`.

## 왜 지금 하나

전환일에 밀리는 건 코드가 아니라 **남이 심사하는 것**이다. 약관 개정은 재동의,
알림톡은 템플릿 재심사 — 둘 다 우리가 당길 수 없다. 코드는 며칠이면 되는데 심사는 아니다.

**카카오는 템플릿을 독립적으로 승인한다.** 기존 승인 템플릿을 건드리지 않고 새 코드로
하나 더 등록할 수 있고, 보내지 않는 승인 템플릿이 있는 건 비용이 0이다. 그래서
"PG 문안" 을 지금 등록해 두면 전환일에는 **env 에 ID 를 넣는 일만** 남는다.

⚠️ **기존 템플릿을 수정하지 말 것.** 수정은 재심사고, 심사 중에는 카카오 본문(구)과
   문자 대체 본문(신)이 어긋난다(docs/34 §하단). 새로 만들어 나란히 둔다.

## 무엇이 바뀌나 — 9종 중 3종

| kind | PG 문안 필요 | 왜 |
|---|---|---|
| `chat_reply` · `chat_message_to_photographer` · `inquiry_received` | — | 결제와 무관 |
| `booking_proposed_to_photographer` · `booking_proposed_to_customer` | — | 결제와 무관 |

| **`deposit_confirmed`** | ✅ | 카드로 낸 고객에게 "입금하신" 은 틀린 말 |
| **`booking_confirmed`** | ✅ | 같은 이유 (작가 쪽) |
| `settlement_paid` | — | "송금액" 은 지급대행에서도 맞다 |

## 등록할 것

아래는 **코드에서 뽑아낸 것**이다(`notify-templates.ts` 의 `pg.body`). 손으로 옮겨
적지 말고 그대로 붙여넣을 것 — 한 글자만 달라도 심사받은 본문과 발송 본문이 어긋난다.

### 예약 수락 — `booking_accepted`

- 수신자: 제안한 쪽
- 변수: `#{상대명}` · `#{촬영일}` · `#{링크}`
- 버튼: 예약 확인하기 → `https://samae.ai/bookings/#{예약ID}`
- 승인 후 넣을 env: `ALIMTALK_TPL_BOOKING_ACCEPTED_PG`

**지금 문안 (무통장 · 승인됨)**
```
[사매] 제안하신 예약을 #{상대명}님이 수락했어요.
· 촬영일: #{촬영일}
입금이 확인되면 예약이 확정돼요. 확인되는 대로 다시 알려드릴게요.
#{링크}
```

**등록할 문안 (PG)**
```
[사매] 제안하신 예약을 #{상대명}님이 수락했어요.
· 촬영일: #{촬영일}
결제가 완료되면 예약이 확정돼요.
#{링크}
```

- 수신자: 고객
- 변수: `#{작가명}` · `#{촬영일}` · `#{링크}`
- 버튼: 예약 확인하기 → `https://samae.ai/bookings/#{예약ID}`
- 승인 후 넣을 env: `ALIMTALK_TPL_DEPOSIT_CONFIRMED_PG`

**지금 문안 (무통장 · 승인됨)**

#{링크}
```

**등록할 문안 (PG)**
```
[사매] 결제가 완료되어 예약이 확정됐어요.
· 작가: #{작가명}
· 촬영일: #{촬영일}

### 입금 확인 (작가) — `booking_confirmed`

- 수신자: 작가
- 변수: `#{고객명}` · `#{촬영일}` · `#{정산금액}` · `#{링크}`
- 버튼: 정산 내역 보기 → `https://samae.ai/studio/settlements`
- 승인 후 넣을 env: `ALIMTALK_TPL_BOOKING_CONFIRMED_PG`

**지금 문안 (무통장 · 승인됨)**

· 촬영일: #{촬영일}

```

```

· 촬영일: #{촬영일}

## 승인된 뒤

`.env`(프로덕션 포함)에 위의 env 키 셋을 넣는다. **넣어도 아무 일이 일어나지 않는다** —
`PAYMENT_MODE` 가 `pg` 가 아니면 코드가 이 키를 쳐다보지도 않는다.

```
ALIMTALK_TPL_BOOKING_ACCEPTED_PG=...
ALIMTALK_TPL_DEPOSIT_CONFIRMED_PG=...
ALIMTALK_TPL_BOOKING_CONFIRMED_PG=...
```

## 코드가 이미 보장하는 것

- **PG 문안이 있는 kind 만** `_PG` 키를 찾는다. 나머지 6종은 지금 ID 를 그대로 쓴다
  (없는 키를 기다리다 전부 문자로 떨어지는 사고 방지)
- PG 로 켰는데 `_PG` 템플릿이 아직 심사 중이면 **무통장 템플릿으로 떨어뜨리지 않는다.**
  차라리 문자로 나간다 — 카드로 결제한 고객이 "입금이 확인되어" 를 받는 것보다 낫다.
  문자 본문은 `notifyBody()` 가 결제 방식에 맞는 걸 고른다
- PG 문안이 원문과 **같은 변수**를 쓰는지 테스트가 막는다. 어긋나면 발송 시점에
  던져서 알림이 통째로 안 나간다
- PG 문안에 "입금"·"계좌" 가 남아 있으면 테스트가 실패한다

## 남은 판단 하나

`booking_accepted` 는 PG 에서 **아예 없어질 수도 있다.** 수락과 결제가 한 동작으로
합쳐지면 "수락했어요" 와 "결제됐어요" 사이에 알릴 틈이 없다. 결제창을 붙이며(docs/42 §3-3)
정해야 하는데, **등록해 두는 쪽이 안전하다** — 안 쓰면 그만이고, 필요해졌을 때 없으면
또 심사를 기다린다.
