# 29. 무료 모델 모집 퍼널 (캐스팅)

> 무료 촬영 모델을 회차제로 모집하고, **탈락자를 서비스 유저로 전환**하는 퍼널.
> 마케팅 맥락·시즌 역산은 `samae-marketing/기획/성장채널_로드맵_2026-08.md` 참조.

---

## 0. 이 기능의 목적

선정되는 사람은 소수(회차당 5~10명)고 **탈락자가 다수**다.
따라서 이 퍼널의 KPI는 "좋은 모델을 뽑았는가"가 아니라 **"신청자가 서비스 유저가 되었는가"** 다.

| 구분 | 지표 |
|---|---|
| 1차 (직접) | 회차별 신청 수 · 모델 확보 수 |
| **2차 (진짜 목적)** | **신청→가입 전환율 · 탈락자의 작가 프로필 열람률 · 다음 회차 재신청률** |

이 목적이 설계의 세 지점에 박혀 있다:
① 신청 폼에서 **작가의 사진을 직접 고르게** 한다 (신청 자체가 탐색 온보딩)
② **로그인을 필수**로 한다 (탈락자 재접촉 채널 확보)
③ **탈락 통지가 종점이 아니라 분기점**이 되게 한다

## 1. 라우트

| 경로 | 역할 | 접근 |
|---|---|---|
| `/casting` | 현재 회차 소개 + 신청 폼 | 공개(열람) / 제출은 로그인 |
| `/casting/done` | 접수 완료 | 로그인 |
| `/casting/my` | 내 신청 상태 조회 | 로그인 |
| `/admin/casting` | 회차·신청 심사 | admin |

`/apply`(작가 신청)와 라우트·테이블을 **분리**한다. 대상도 심사 기준도 다르다.

### 로그인 타이밍 — 폼을 먼저 보여주고 제출 시 요구

작가 신청(`/apply`)은 진입 시점부터 로그인 필수지만, 캐스팅은 **콜드 오가닉 트래픽**이 유입원이다.
스레드·디시에서 온 사람에게 첫 화면이 로그인 벽이면 대부분 이탈한다.

```
페이지 열람·폼 작성 (비로그인 가능)
   → 제출 버튼 클릭
   → 미로그인이면 입력값을 sessionStorage 에 보존하고 카카오 로그인으로
   → 복귀 후 폼 자동 복원 → 제출
```

카카오 소셜이 2탭이라 이 지점의 이탈은 크지 않다. **무엇을 신청하는지 본 뒤에 로그인**하는 순서가 중요하다.

## 3. 미성년 분기 — 이 기능의 핵심 가드

법적 배경은 `기획서_한림예고_모델학과_협력.md` 5장. 여기서는 구현 규칙만 정리한다.

게이트를 **접수 시점과 선정 시점 두 단계로 나눈다.**

```
[접수 게이트]  birth_date 입력
   │
   ├─ 만 15세 미만 ────→ ❌ 차단  "만 15세 이상부터 신청하실 수 있어요"
   │
   ├─ 만 15세 ~ 18세 ──→ ⚠️ 보호자 성명·연락처 필수 (동의서는 아직 아님)
   │                      + 동의서 양식 PDF 다운로드 안내
   │
   └─ 만 19세 이상 ────→ ✅ 일반 접수


[선정 게이트]  status → 'selected'
   │
   └─ 만 19세 미만 ────→ 보호자 서명 동의서 파일이 없으면 ❌ 선정 불가
```

### 동의서를 접수 시점에 강제하지 않는 이유

인쇄 → 서명 → 스캔은 이탈률이 매우 높다. 미성년 신청자를 접수 단계에서 통째로 잃는다.

**법적 위험이 실제로 발생하는 지점은 신청서 보관이 아니라 촬영·게시다.**
따라서 리드는 일단 확보하고, 게이트는 위험이 발생하는 지점(선정)에 건다.
접수 단계에서 보호자 **연락처**를 받아두므로 운영진이 직접 회수를 독촉할 수 있다.

개인정보 측면으로도 문제없다 — 만 14세 이상은 본인 동의로 개인정보 수집이 가능하고
(15세 미만은 어차피 차단), 법정대리인 동의가 필요한 것은 **초상 이용이라는 법률행위** 쪽이다.

### 반드시 지킬 것

1. **DB 트리거가 최종 방어선이다.** 클라이언트 분기나 서버 액션 검증만으로는 안 된다.
   `casting_application_age_gate()` 가 insert·update마다 만 나이를 재계산해 두 게이트를 모두 강제한다.
2. **어드민 UI에서도 하드 가드.** 동의서 미제출 미성년은 **선정 버튼이 비활성화**된다.
   트리거에서 막히면 에러 화면을 보게 되므로, UI에서 먼저 막아 운영 경험을 지킨다.
3. **만 나이는 `birth_date` 기준으로 항상 재계산한다.** 신청 시점 나이를 컬럼에 박아두지 않는다
   (촬영 시점에 생일이 지나 성년이 되는 경우가 있다).
4. **CHECK 제약을 쓰지 않는다.** 만 나이 판정에 `current_date`가 필요한데
   CHECK는 immutable 표현식만 허용한다. 그래서 트리거다.

구현: `supabase/migrations/0084_casting_funnel.sql`

## 4. 신청 폼 구성

한 화면에 다 넣으면 이탈한다. **4스텝**으로 쪼갠다. 진행바를 보여준다.

```
STEP 1  기본 정보     이름 · 연락처 · 생년월일 · 지역
                     └─ 생년월일 입력 즉시 미성년 여부 판정 → 스텝 구성이 바뀜

STEP 2  사진 고르기   참여 작가들의 실제 포트폴리오 사진 그리드에서 1~3장 선택 (필수)  ← 온보딩 핵심
                     작가명은 사진 위에 얹어서 자연스럽게 학습되게
                     "희망 사항이며 실제 배정은 작가 일정에 따라 달라질 수 있어요" 명시

STEP 3  내 사진·컨셉  전신/얼굴 1~3장 · 희망 무드 태그 · 자유 서술(선택)

STEP 4  동의          참여(필수) / SNS 게시 / 유료 광고 / 크레딧 표기
                     └─ 미성년이면: 보호자 정보 + 동의서 양식 다운로드 + 서명본 업로드
```

### STEP 2를 필수로 두는 이유 · 왜 작가가 아니라 사진인가

여기가 이 기능이 존재하는 이유다.
신청자는 **선정 여부와 무관하게 사진을 훑고 취향을 판단하는 경험을 이미 끝낸 상태**가 된다.
배너 노출 100회보다 강한 온보딩이다.

**작가 이름 목록에서 고르게 하면 안 된다.** 사람은 이름으로 취향을 판단하지 않는다.
이름 목록은 "아무나 하나" 누르고 넘어가는 화면이 되지만, 사진 그리드는 실제로 탐색 탭과 같은 경험이 된다.
게다가 탈락 통지에 **"고르셨던 이 사진"** 을 그대로 되돌려 보여줄 수 있다 —
작가 프로필 링크보다 훨씬 강한 전환 소재다. 본인이 좋다고 표시한 바로 그 이미지이기 때문.

**그리드는 작가별 라운드로빈으로 섞는다.** 최신순으로 나열하면 사진이 600장인 작가가 그리드를 독점해
나머지 작가는 선택지에서 사실상 사라진다. `interleaveByPhotographer()` 가 작가당 15장씩 번갈아 담아 최대 60장.

⚠️ **포트폴리오가 없는 참여 작가는 그리드에 나올 방법이 없다.** 사진이 곧 선택지이기 때문이다.
회차를 열기 전에 참여 작가 전원의 사진이 등록됐는지 확인해야 한다
(운영자로 로그인하면 `/casting` 상단에 누락 작가 경고가 뜬다).

"상관없어요" 옵션은 두지 않는다. 그 옵션이 있으면 대부분 그걸 누르고, 장치가 무력화된다.

### 동의 항목을 쪼개는 이유

기획서 5-2와 동일한 원칙이다. **SNS 게시·유료 광고에 동의하지 않아도 신청은 가능**해야 한다.
동의 항목을 하나로 묶으면 법적으로 취약하고(포괄동의), 심리적 저항도 커진다.

기존 `albums.ad_consent` 가 backfill 때문에 실제 동의와 구분이 안 돼 공식 계정 발행이 막혀 있는데,
**이 테이블은 처음부터 항목을 분리해서** 같은 문제를 만들지 않는다.

## 6. 탈락 통지 = 전환 장치

**여기가 이 퍼널의 실제 수익 지점이다.** 탈락 메시지를 사과문으로 쓰면 안 된다.

인앱 `notifications` + (연동 시) SMS로 발송. `notification_type` 은 기존 `system` 재사용.

```
아쉽게도 이번 회차에는 함께하지 못하게 되었어요.

  · 다음 회차 대기 명단에 자동으로 등록해 두었어요 (알림 받으실 수 있어요)
  · 신청 때 고르셨던 사진들이에요  [썸네일 1] [썸네일 2] [썸네일 3]
    → 각 사진을 누르면 사진 상세로, 거기서 작가에게 바로 문의할 수 있어요
```

각 줄이 다른 일을 한다:
1. **재방문 명분** — "끝"이 아니라 "대기 중"이라는 상태를 준다
2. **전환 링크** — 본인이 좋다고 표시한 바로 그 사진이라 클릭률·전환율이 콜드 트래픽과 비교가 안 된다
3. **탐색 유도** — 사진 상세 → 작가 → 문의로 이어지는 기존 동선에 그대로 올려보낸다

미선정자에게 **할인 코드를 붙일지는 정훈 결정 사항**이다(아래 8장).

## 7. 계측 (Mixpanel)

기존 `mpTrackServer` / `mp` 패턴을 따른다.

| 이벤트 | 시점 | 속성 |
|---|---|---|
| `Casting View` | `/casting` 진입 | round_slug, utm_* |
| `Casting Step` | 스텝 이동 | step, round_slug |
| `Casting Submit` | 접수 완료 | round_slug, is_minor, photographer_count |
| `Casting Abandon` | 스텝 이탈 | last_step ← **어느 스텝에서 죽는지** |
| `Casting Result Viewed` | 결과 확인 | result |
| `Casting → Photographer` | 탈락 통지 링크 클릭 | **2차 KPI 그 자체** |

`Casting Abandon`의 `last_step`이 폼 개선의 유일한 근거다. STEP 2(작가 고르기)가 필수라
여기서 이탈이 몰릴 가능성이 높은데, **몰리더라도 STEP 2를 없애면 안 된다** — 기능의 목적 자체가 사라진다.
대신 선택 최소 개수를 3→1로 낮추는 식으로 조정한다.

PII(이름·전화·생년월일)는 **절대 전송하지 않는다.** `is_minor` 같은 파생 불리언만 보낸다.

## 8. 구현 순서

작업 단위 원칙에 따라 4청크로 쪼갠다. 각 청크는 독립적으로 동작한다.

| 청크 | 산출물 | 완료 기준 |
|---|---|---|
| **1** | 마이그레이션 + `/casting` 신청 폼 + 제출 서버액션 | 로그인 사용자가 신청 접수, 미성년 분기 서버 검증 동작 |
| **2** | `/admin/casting` 심사 화면 | 회차별 신청 조회·선정/탈락 처리, 동의서 하드가드 동작 |
| **3** | 결과 통지 + 탈락 전환 동선 + 대기열 + 파기 배치 | 회차 일괄 통지 발송, 링크 클릭 계측 |
| **4** | 오가닉 광고 소재 (스레드·인스타 3계정) | 마케팅 공장 파이프라인에 연결 |

**9월 첫 주 오픈 데드라인**을 맞추려면 청크 1·2가 최소 요건이다.
청크 3은 첫 회차 마감(9월 하순) 전까지만 되면 된다.

## 9. 결정된 사항

작가도 모델도 돈을 주고받지 않는다. 양쪽 다 결과물을 가져가는 구조다.

| | 내는 것 | 받는 것 |
|---|---|---|
| 모델 | 시간 | 촬영 원본·보정본 전량 (사용 제한 없음) |
| 작가 | 시간·장비·보정 | 작품·포트폴리오 · 사매 공식 계정 노출·크레딧 |

**이 구조를 신청 폼에 명시해야 한다.** "무료"만 강조하면 신청자가 숨은 비용을 의심한다.

동시에 **모델의 노쇼를 억제**한다 (상대도 무보수로 시간을 쓴다는 사실이 책임감을 만든다).
