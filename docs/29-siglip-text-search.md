# 29. SigLIP2 검색어 기반 사진 검색 (2026-08-25)

> 문서 상태: 로컬 코드·HTTP 통합 검증 완료 · 화면 수동 확인 필요 · 배포 전
>
> 작업 브랜치: `dev`

## 1. 목표

사용자가 홈 검색창에 자연어를 입력하면 SigLIP2가 검색어를 텍스트 임베딩으로 변환하고, 기존 사진 임베딩과 가까운 공개 사진을 보여준다.

기본 결과는 **SigLIP2 텍스트→이미지 유사도순**을 사용한다. 다만 사진 태그·앨범 제목·앨범 설명처럼 사진과 직접 연결된 메타데이터가 검색어 원문에 일치하면 해당 사진을 우선하고, 유사도가 비슷한 후보 안에서는 홈 추천과 같은 앨범·방향 다양성 규칙을 적용한다.

## 2. 확정 범위

- 모델은 현재 사진 임베딩과 같은 `google/siglip2-so400m-patch16-naflex`를 사용한다.
- 검색창은 홈 히어로 바로 아래, 검색 결과 상단, 사진 상세의 유사사진 영역 위에 노출한다.
- 검색어는 `/?q=<검색어>`로 유지해 새로고침·공유·뒤로가기를 지원한다.
- 문자열 점수와 벡터 거리를 수치로 가중합하지 않는다. 직접 일치 사진을 우선하고, 직접 일치가 부족할 때만 SigLIP2 결과로 보충한 뒤 다양성 재정렬을 적용한다.
- 방향 의도가 없는 검색은 무한 스크롤의 모든 48장 구간을 세로 36장·그 외 12장으로 고정한다. 세로·그 외 후보 큐를 독립 순환하므로 세로 후보가 부족하면 전체 고유 후보 소진 전에 세로 사진이 먼저 반복되며, 모든 후보는 결국 노출한다. 최유사 1위는 첫 위치에 보호하고 동일 앨범은 최근 12장 내 재노출을 피한다.
- `가로`, `세로`, `portrait`, `landscape`처럼 방향 의도가 명시된 검색은 75% 세로 규칙을 적용하지 않는다.
- RRF, 패키지명·패키지 설명 검색, 검색 필터 UI, 검색 자동완성은 이번 범위에서 제외한다.
- 검색 로그는 기존 `search_logs` 경로를 유지한다.

## 3. 데이터 흐름

```text
검색창 제출
  → Next.js 서버에서 두 검색을 병렬 실행
    → 사진 태그·숨김 태그·앨범 제목·설명·장소·작가 메타데이터 직접 일치
    → 맥미니 POST /embed-text → SigLIP2 1152차원 벡터 → similar_photos_by_vector
  → 직접 일치 사진의 실제 RPC 거리·앨범 ID를 보존하고 유사도순으로 정렬
  → 48장마다 직접 일치 최대 36장 + 고유사도 벡터 전용 최대 12장을 후보로 구성
  → 한쪽 후보가 부족하면 다른 후보로 채워 고유 후보를 최대 300장 확보
  → 고유 후보 소진 후에는 검색 상단 순위를 건드리지 않고 사이클별 새 순서로 반복 노출
  → 48장 관련도 구간별 직접 일치·벡터 후보 병합과 앨범 분산 → 화면에서 방향별 큐를 독립 순환 → 방향 의도가 없으면 매 48장마다 세로 36장·그 외 12장 고정
  → 홈 메이슨리 그리드에 표시
```

텍스트와 사진은 동일한 SigLIP2 임베딩 공간에 놓인다. 사진 임베딩의 모델·차원과 검색어 임베딩의 모델·차원이 다르면 비교하지 않고 실패 처리한다.

## 4. 구성요소

### 4.1 맥미니 텍스트 임베딩 API

`scripts/embed/serve.py`에 `POST /embed-text`를 추가한다.

요청:

```json
{ "texts": ["푸른 숲속 커플 사진"] }
```

응답:

```json
{
  "vectors": [[0.01, -0.02]],
  "count": 1,
  "infer_ms": 12,
  "model": "google/siglip2-so400m-patch16-naflex"
}
```

- 기존 `PERSONA_SERVICE_TOKEN` 인증을 그대로 사용한다.
- 공백 제거 후 1~120자만 허용한다.
- 한 요청의 검색어는 최대 8개로 제한한다.
- 기존 상주 SigLIP2 모델을 재사용하고 별도 모델을 띄우지 않는다.

### 4.2 앱 서버 클라이언트

`src/lib`의 서버 전용 모듈이 `/embed-text`를 호출한다.

- 브라우저가 맥미니 주소나 서비스 토큰을 직접 알지 못하게 한다.
- 응답 벡터가 1152차원인지 검증한다.
- 연결 실패·타임아웃·잘못된 응답은 예외를 사용자 화면까지 전파하지 않고 벡터 후보만 빈 결과로 처리한다. 사진 태그·앨범 제목·설명에 직접 일치한 메타데이터 후보는 계속 노출한다.
- 검색어의 원문은 서버 로그에 남기지 않는다. 기존 집계용 `search_logs`만 사용한다.

### 4.3 벡터 검색

기존 `similar_photos_by_vector(halfvec, integer)` RPC를 서버의 service role로 호출한다.

- 최대 300개의 고유 후보를 요청하고 각 사진의 코사인 거리와 앨범 ID를 앱까지 보존한다. 화면에서는 세로·그 외 후보 큐가 각자의 고유 후보를 먼저 소진하고 이후 결정적 셔플로 독립 순환한다.
- 최유사 후보와 직접 일치 후보는 보호하고, 나머지는 앨범·방향 뭉침을 해소하는 범위에서 재배치한다.
- 앱에서 `GalleryPhoto`에 필요한 작가·가격·지역 메타데이터를 사진 ID로 다시 조회한다.
- 비공개 사진, 미승인 작가, `feed_hidden=true` 사진은 최종 결과에서 제외한다.
- 결과가 부족하더라도 이번 검증 버전에서는 무관한 일반 사진을 뒤에 붙이지 않는다.

## 5. DB 변경 여부

첫 버전은 신규 테이블·컬럼·인덱스·함수를 만들지 않는다.

재사용 대상:

- `photos.embedding halfvec(1152)`
- 사진 임베딩 HNSW 인덱스
- `similar_photos_by_vector` (`0079`)
- 기존 `search_logs`

구현 전에 운영 DB에 `similar_photos_by_vector`가 실제 배포되어 있는지만 읽기 전용으로 확인한다. 함수가 없거나 현재 앱의 노출 규칙을 안전하게 만족시키지 못해 DB 수정이 필요해지면 **마이그레이션을 적용하지 않고 사용자에게 먼저 알린다.**

## 6. UI

### 홈

`FeedHero` 아래, 사진 피드 위에 모서리가 작은 사각형 검색창을 배치한다.

- 검색창의 원래 위치가 화면 상단을 지나면 같은 검색창을 상단에 고정한다. 아래로 이동 중인 고정 검색창은 내부 배경과 문구를 완전히 투명하게 만들고 테두리도 옅은 반투명 색으로 낮춘다. 위로 스크롤하거나 마우스를 올리거나 입력 포커스를 받으면 배경색·문구·기본 테두리를 즉시 복구한다.
- 입력창 플레이스홀더는 공개 사진에서 함께 자주 쓰이는 한국어 태그 조합 중 하나를 요청마다 선택한다. 예: `데이트 커플스냅`, `가을 감성`, `빈티지 필름`.
- 입력창 아래의 별도 예시 문구는 표시하지 않는다.
- 돋보기는 기본 브랜드 빨강이고 입력 포커스 시 테마 본문색(다크 모드 흰색·라이트 모드 검정색)으로 바뀐다.
- 마우스 호버·키보드 포커스 시 브랜드 빨강(`#ff3d2e`) 광택의 앞쪽 끝이 검색창의 실제 SVG 외곽선 왼쪽 위 모서리에서 시작한다. 1.5초 동안 테두리를 한 바퀴 완전히 돌아 앞쪽 끝이 다시 왼쪽 위 모서리에 도착한 뒤, 이동 없이 그 자리에서 사라진다. 한 검색창 인스턴스에서는 최초 1회만 재생하며 다른 화면의 새 검색창에서는 다시 재생한다. 모션 최소화 환경에서는 애니메이션을 끈다.
- 검색 제출 시 `/?q=`로 이동한다.

### 검색 결과

- 홈 히어로는 숨기고 결과 상단에 같은 검색창을 표시한다.
- 사진 상세와 동일하게 화면 왼쪽 위에 고정 뒤로가기를 두고, 검색창은 버튼 오른쪽부터 시작한다. 홈·상세와 같은 스크롤 투명화와 호버·포커스·위쪽 스크롤 복구 효과를 적용한다.
- 입력값은 현재 `q`로 유지한다.
- 상위 결과를 48장씩 점진 노출하며, 하단 센티넬에 닿으면 다음 48장을 이어서 보여준다.
- 검색어별로 불러온 결과와 스크롤 위치를 분리된 세션 키에 유지한다. 최대 300개의 고유 후보를 방향별 큐로 나눠 48장씩 노출하고, 각 큐가 고유 후보를 소진하면 독립 순환해 실제 무한 스크롤을 유지한다.
- 결과가 없으면 `다른 장면이나 분위기로 검색해보세요`를 표시한다.
- 검색어를 지우고 제출하면 `/`로 돌아간다.
- 하단 홈 탭을 다시 눌러도 검색 상태를 버리고 기본 홈 최상단으로 돌아간다.

### 사진 상세

- 상세 페이지 최상단에서 대표 사진 바로 위에 같은 검색창을 표시한다.
- 뒤로가기는 화면 왼쪽 위의 기존 반투명 고정 버튼을 유지한다. 검색창은 같은 상단 행에서 버튼과 겹치지 않도록 왼쪽 여백을 두고 오른쪽부터 배치하며, 화면 상단에 고정된 동안에는 홈과 동일한 투명·사용 의도 노출 규칙을 적용한다.
- 검색 제출 시 홈의 `/?q=` 검색 결과로 이동한다.

## 7. 장애 처리

- 맥미니가 꺼졌거나 타임아웃이면 SigLIP2 벡터 후보는 비우되 사진 태그·앨범 제목·설명에 직접 일치한 메타데이터 후보는 유지한다.
- 메타데이터 직접 일치는 `만삭`·`돌`처럼 시각 모델만으로 찾기 어려운 촬영 목적을 보강하는 확정 검색 경로이며, 임의의 광범위 문자열 폴백은 사용하지 않는다.
- 홈 일반 피드와 사진 상세 유사도 추천은 검색 장애의 영향을 받지 않는다.

## 8. 검증

- `encode_text()`가 1152차원 정규화 벡터를 반환하는지 확인한다.
- `/embed-text` 인증·입력 제한·응답 형식을 테스트한다.
- 앱 클라이언트의 정상 응답·타임아웃·차원 불일치를 테스트한다.
- 벡터 RPC 결과가 공개 사진·승인 작가·`feed_hidden=false`만 노출하는지 확인한다.
- `웨딩`, `푸른 숲속 커플`, `어두운 실내 플래시 인물`, `바다에서 뛰는 사람` 등 대표 검색어로 결과를 눈으로 비교한다.
- 홈과 결과 화면의 모바일·데스크톱 배치, 뒤로가기, 검색어 유지, 빈 결과를 확인한다.

## 9. 배포 순서

1. 맥미니 런타임에 `/embed-text`를 먼저 반영한다.
2. 인증된 요청으로 모델명·벡터 차원·지연시간을 확인한다.
3. 운영 DB의 기존 `0079` RPC 존재 여부를 읽기 전용으로 확인한다.
4. 앱 검색 UI와 서버 검색 경로를 배포한다.
5. 검색 로그와 대표 검색어 결과를 확인한다.

앱 배포 전에 맥미니 API가 준비되어야 메타데이터 직접 일치가 없는 자연어 검색도 정상적으로 사진을 찾을 수 있다.

## 10. 구현·검증 결과 (2026-08-26)

- `dev`에서 `POST /embed-text`와 홈 검색 UI를 구현했다.
- 실제 응답 모델은 `google/siglip2-so400m-patch16-naflex`, 벡터 차원은 1152로 확인했다.
- 운영 DB의 기존 `similar_photos_by_vector` RPC가 정상 응답했다. **DB 마이그레이션은 만들거나 적용하지 않았다.**
- 워밍된 로컬 모델에서 대표 검색어 텍스트 임베딩은 26.2~94.5ms, RPC는 47.6~898.9ms였다.
- `푸른 숲속 커플 사진`, `어두운 실내 플래시 인물`, `바다에서 뛰는 사람` 세 검색어 모두 상위 8개 결과를 반환했다.
- 로컬 `http://localhost:3000/`과 검색 URL이 HTTP 200을 반환했고, 검색 결과 첫 화면에 48개 카드가 서버 렌더링됐다.
- 검색 고유 후보 상한을 300장으로 확대했다. 기존 갤러리 센티넬로 48장씩 노출하고, 300장 소진 뒤에도 센티넬을 유지해 사이클별 새 순서로 계속 이어지게 했다.
- 포트폴리오 메타데이터 직접 일치 결과를 SigLIP2 앞에 병합했다. 다단어 검색은 원문 단어를 모두 포함할 때만 승격해 일부 흔한 단어가 벡터 순서를 덮지 않게 했다.
- 직접 일치 사진은 실제 SigLIP2 거리로 다시 정렬한다. 각 48장 관련도 구간은 직접 일치 최대 36장과 벡터 전용 최대 12장으로 구성해 고유사도 사진을 상단에 유지하면서 다른 포트폴리오를 분산 후보로 사용한다.
- 검색 화면의 메이슨리는 사진 높이뿐 아니라 동일 앨범의 좌우 겹침과 세로 연속을 함께 고려한다. 일반 홈 피드의 기존 컬럼 배치는 변경하지 않는다.
- 단, 열 높이가 반 장 이상 벌어지면 앨범 분산보다 짧은 열을 우선한다. 분산 점수 때문에 한쪽 열이 비는 현상을 방지한다.
- 검색 후보 생성과 홈·상세 유사사진 추천은 공통 앨범 다양성 재정렬기를 사용한다. 서버는 원본 관련도순을 48장씩 나눠 각 구간 안에서 동일 앨범의 12장 간격을 목표로 한다. 화면의 무한 스크롤은 방향별 후보 큐를 별도로 순환해 모든 48장 구간을 세로 36장·그 외 12장으로 고정한다. 이 비율 보장을 위해 세로 후보가 부족하면 세로 사진이 먼저 반복되고 뒤 관련도 구간의 세로 후보가 앞 화면에 포함될 수 있으며, 최고 유사도 1위는 첫 위치에 보호한다.
- `가로 사진`, `세로형 프로필`, `horizontal` 등 방향 의도가 있는 검색에서는 세로 75% 규칙을 끈다. `가로수길`처럼 방향이 아닌 단어는 예외로 판정한다.
- 운영 데이터에서 `만삭` 직접 일치 사진 6장이 검색 결과 0~5번에 배치되고, `푸른 숲속 커플 사진`은 기존 SigLIP 상위 8개 순서를 유지하는 것을 확인했다.
- 운영 데이터의 `한복`·`가을` 검색 모두 300장 후보와 48장 단위 점진 노출을 확인했다. 첫 48장의 동일 앨범 좌우 겹침은 기존 배치에서 각각 10회·13회였고 새 검색 메이슨리에서 모두 0회였다.
- Python 검색 API 테스트 4개와 전체 Node 테스트 107개, TypeScript 검사와 프로덕션 빌드가 통과했다. 신규 검색 루프·메이슨리 파일 ESLint에도 오류가 없었다.
- 전체 저장소 ESLint에는 이번 변경과 무관한 기존 오류 21개가 남아 있다.
- 자동 브라우저 연결이 제공되지 않아 스크린샷·클릭 자동화는 실행하지 못했다. 3000 서버를 유지해 실제 화면을 수동 확인할 수 있다.
